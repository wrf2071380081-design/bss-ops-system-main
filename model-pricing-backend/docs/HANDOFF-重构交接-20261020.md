## 1. 已确认口径（以此为准，别再猜）

1. **权限 = 身份/绑定，不是角色**
   - 读取：内部全员可见所有数据。
   - 操作：部分动作只有**绑定/特定的人**能做（客户绑定的销售、模型采购人、节点办理人）。
   - 没有"财务/客户"等角色划分；权限基础设施保留，业务不删可注释，未来上角色再开。
2. **无审批**（这一版不引入）。
3. **客户不登录 BSS**：客户线上沟通，报价单**导出 Excel（字段待定）微信发客户**。
4. **定价**：去掉通道费、折损率；`成本 = 官方价 × 采购系数 c`；`毛利 g = 1 − c/s`；`s = c/(1−g)`。
   **毛利 >3% 正常，<3% 允许但操作者二次确认并留痕**。
   ⚠️ 原型当前是"毛利<30% 预警"（源码 `i.margin<.3`），**要改成 3%**。
5. **测试**：先做成**供应商自己触发**；**没有测试不能提交报价**；**连通测试失败硬拦截**；其他指标不设明确阈值。
   复测后续再定。
6. **正式接口配置与测试凭据分开存**。
7. **授信 = 额度**（credit limit）：供应商→我方（采购授信）、我方→客户（销售授信），带版本记录，不是流程。
8. **标准模型库要自动拉取官方模型信息**，不能长期人工填（见 §5）。

## 4. 交互细节（已核实）

### 4.1 排序 / 筛选
- **列头排序**：点列头切升序/降序，**空值始终排末尾**（`toggleResourceSort`，模型广场与报价两处）。
- 筛选维度：平台（全部/国内/海外）、供应商、模型公司、模型类型（文本/图片/视频/音频）、部署节点、状态。

### 4.2 绑定式操作门
- 原型用 `authorize('运营'|'研发'|'商务')` + 右上角切换成员实现；真实系统要落成**具体人绑定**（assignment）。
- 原型 `opLeader()` 做领导审批——**这一版去掉**。

### 4.3 校验规则（改代码要照着做）
- 标准模型资料：官方身份、规格、能力、API、生命周期、来源、核验日期必须完整，否则"暂不可报价"。
- 报价：每个模型必须选**可用供应来源**且官方价完整；**不能跨区域报价**；正式客户的国内/海外属性不可改。
- 供应商：模型、供方名称、**采购系数 ∈ (0,1]** 必填。
- 报价：毛利率必须 <100%；毛利率或销售系数至少填一个。
- 开通：同一模型已有有效开通/进行中流程 → 拒绝重复申请。
- 申报：原型"至少一行测试通过"；**按新口径改为"每行都要有测试且连通通过"**。

### 4.4 状态机
- 资源：`待测试 / 待接入 / 已接入 / 已下架`（下架计划：`下架计划 / 上架计划`）。
- 客户开通：`已开通 / 待禁用 / 禁用待执行 / 供应下架停止`。
- 合同：`办理中 / 已归档`。
- 申报：原型 `待审批 / 通过` → **改为无审批的办理状态**（测试与资源配置、合同与授信、价格已生效、接入完成）。
- 流程节点：`prep 账户与接口准备(运营) → config 资源配置(运营) → test 模型测试(研发) → contract 合同签署(商务) → credit 授信开具(商务) → account 账户开通 → execute 执行操作`。

## 5. 标准模型库自动拉取：规则 vs 大模型（回答你的问题）

**结论：不是二选一，必须"规则 + 大模型"混合，且价格必须人工确认。**

### 5.1 各字段可行性

| 字段 | 规则能否稳拿 | 建议 |
|---|---|---|
| 模型名称 / 官方 ID / 厂商 | 高 | 走厂商 `models` API 或官方模型列表，规则抓 |
| 上下文长度 / 最大输出 | 高 | models API 常返回，规则抓 |
| 模型类型 / 输入输出模态 | 中 | 官方 API 有 modality 字段可规则；跨厂商命名不一，缺的用 LLM |
| 核心能力（thinking/FC/结构化输出/流式/缓存） | 中低 | 文档表述差异大，**LLM 抽取**更稳 |
| **官方价格 / 计费单位** | **低** | 极少有 API 给价格，几乎都在定价页 HTML；**LLM 抽取 + 人工核验** |
| API / 限流 / 访问条件 | 低 | 文档/控制台，**LLM** |
| 发布 / 版本 / 生命周期 | 中 | 部分 API 有 created/deprecated，其余 LLM |

### 5.2 推荐方案（分层）

1. **规则适配器**（确定性）：按厂商（OpenAI/Anthropic/Google/阿里/DeepSeek…）优先走官方 API，拿列表、ID、上下文、模态；拿不到的字段留空。
2. **LLM 抽取兜底**：把官方定价页/文档页转 markdown，用**固定 JSON Schema** 抽取，要求返回
   `source_url + 原文片段`，并给置信度；低置信标"待核实"。
3. **暂存 + 差异 + 人工确认**：定时拉取 → 生成 draft → 与现值 diff → 人工确认 → 生效。
   **价格绝不能静默覆盖**（这是钱）。人工只处理差异/异常，不用逐条填。
4. **定时变更检测**：页面 hash 不变不重复抽（省 LLM 成本）；变化才生成 draft。
5. **审计**：存 `source_url`、抓取时间、原文片段、确认人，满足可追溯。

> 这正好复用原 M2 的"抓取任务 + 暂存区 + 确认"，所以 **M2 保留改造，不是休眠**。

## 6. 自动测试平台对接（open-api v1）

- 角色：BSS 是**实名调用方**，用 `Authorization: Bearer <token>`。
- 四件事：`POST /test-jobs`（带 `Idempotency-Key`）→ `GET /test-jobs/{id}` / SSE → `GET /report?format=json|md|csv|xlsx` → 回调 `job.completed`。
- 门类：`health / baseline / functional / evaluation / intelligence / stress / imagespec`。
- `target`：model / base_url / protocol / api_key（加密、脱敏）；`owner`=供应商；结果看 `verdict`、`summary`。
- 指标：`summary` 的 availability/error_rate/ttft_ms/tpot_ms/sample_count；stress 另有 RPS/TPS
  → 对应原型"连通耗时 / RPS / TPS"。
- 回调：at-least-once；`event_id=evt_<job_id>_<status>` 幂等；`X-Signature` HMAC-SHA256（±300s）；用原始 body 验签。
- 复测：`schedule_at` 定时、`review_of` 复查（这一版先不管）。
- **流程改动**：原型测试是内部研发触发；按新口径要**在供应商门户加"发起测试"**，
  测试通过（至少连通通过）才允许提交报价。

### 6.1 供应商自测流程（按 PM 截图确认）

供应商「申报 → 发起申报 → 模型新增」一行里：

| 列 | 含义 |
|---|---|
| **供方模型名称** | 供应商自己的叫法（如 `deepseekv3`），**可能与官方名不一致** |
| **平台标准模型** | 厂商官方标准名（如 `DeepSeek-V3`），从下拉选；形成"供方名 ↔ 官方名"映射 |
| URL / Key | 该资源的上游地址与凭据（**测试凭据**，与正式接口配置分开存） |
| **采购系数** | (0,1]，成本 = 官方价 × 系数 |
| **参与测试** | 勾选本行要测 |
| 连通性 / 压力测试 | 结果列：`未测试 / 通过 / 不通过` |

流程：新增行 → 填供方名/选标准模型/URL/Key/系数 → **勾"参与测试"** → 点「测试与选模型」
→ BSS 用 `target={model: 平台标准模型, base_url: URL, api_key: Key}` 向测试平台发
`POST /test-jobs`（category 用 health 做连通、stress 做压力）→ 结果回填到该行。

**提交校验（已确认）**：整批申报**至少一条**模型连通+压力测试通过即可提交（不是逐条都要）；
**连通失败的行不能算通过**；其他指标暂不设阈值。

## 8. 目标数据模型草案

- `catalog`（标准模型）：公司、类型、输入输出、容量、能力、官方价/计费单位、API/限流、生命周期、来源/核验日期。
- `resource`（供应来源）：supplier、**standard_model_id（平台标准模型/官方名）**、**supplier_model_name（供方模型名称）**、platform、采购系数、**测试凭据（URL/Key）**、**正式接口配置（另一套）**、参与测试标记、测试指标/报告、状态、归属采购人。
- `link`（客户开通）：customer、resource、model、状态、销售系数、报价快照、客户要求、归属销售。
- `supplier` / `customer`：主体（国内/海外）、服务状态、税率、币种。
- `submission`（申报）：类型（供应商新增/模型新增/价格变更）、rows、版本、状态。
- `batch`（办理批次）：模型、测试结果、配置完成、状态、办理人。
- `contract` / `credit`：合同、授信额度（方向、版本）。
- `test_report`：job_id、verdict、summary、report_url、场景、文件、测试人。
- `plan` / `notice`：上下架计划、公告。
- `assignment`：绑定关系（销售归属、采购人、节点办理人）。
- `audit`：操作留痕（含二次确认）。
