# 现有接口对原型 v0.19 的覆盖度审计（修正版 · 2026-10-20）

> 修正说明：上一版低估了现有能力，把"SKU/型号族、供应商报价、价目表、model_application、
> customer_price_book"当成了"缺失/需大改"。本版逐条回代码核实后订正。
> 方法：`internal/api/router.go` 103 条路由 + model/supplier/customer/price 域结构体 + repo 查询。

---

## 一、先回答你的四个问题

### Q1：SKU/型号族 = 标准模型吗？
**基本是。** 现有 `vendor`（厂商）+ `model_family`（型号族）+ `model_sku`（具体模型）三层，
`model_sku` 已含：`sku_code`、`model_type`、`context_window`、`capability`、`lifecycle_status`、
`cross_border`、`native_currency`、`verify_status`、`sunset_date`。
≈ 原型的 standard_model（厂商/类型/名称/官方ID/容量/能力/生命周期）。
**缺**：`price_items`（官方价明细）、`abilities` 细分、`api_access`（限流/访问条件）、`sources`、`checked_at`。
→ 结论：**复用为主，补字段**，不是重建。

### Q2：供应商报价逻辑相差大吗？
**不大。** 现有 `quote_sheet` + `quote_component`（`component_type` + `multiplier` + `unit_price`）
+ 版本（`version_no`）+ 有效期（`valid_from/to`）+ 审批结论。
原型要的"采购系数 + 逐模型明细 + 版本"和它同构。
→ 结论：**去掉审批状态/审批动作，补"供方模型名、URL/Key、参与测试"即可复用主体逻辑。**

### Q3："供应来源 resource"是什么？
原型里的 resource = **一条"接入"**：
`供应商 × 标准模型 × 部署平台（国内/海外）`，带
**供方模型名称、采购系数、测试凭据（URL/Key）、测试结果（连通/RPS/TPS）、状态、归属采购人**。

现有系统里没有一张叫 resource 的表，但这些信息**散在多处**：
- 供应商主体：`supplier_profile`
- 模型：`model_sku` / `model_family`
- 价格/倍数：`quote_sheet` / `quote_component`
- 授信：`supplier_profile.credit_line`
→ 结论：**概念不是全新的，但缺一个"按接入聚合"的实体**。要么新建 resource 表，要么在现有表上聚合视图；
建 resource 更干净（也对应新迁移 000033）。

### Q4：申报/办理/客户创建/详情/开通/合同授信/计划公告，确定都没有？
逐条核实结果：

| 原型概念 | 现有最接近 | 结论 |
|---|---|---|
| 申报 submission | `model_application`（SUBMITTED/MERGED/APPROVED/REJECTED） | **有雏形，但不够**：单模型、无多行/URL/Key/系数/参与测试/多版本 |
| 办理流程（6 节点） | 无；只有 `todo_task`（待办）+ `change_request` 的审批步骤 | **确定没有** |
| 客户创建 | 无 `CreateCustomer` | **确定没有**（客户只能种子/手工） |
| 客户详情 | 只有 `GET /customers/:id/quote-context`，无通用详情 | **没有独立详情** |
| 客户开通 | `customer_price_book`（客户×SKU 生效价，source=QUOTE/CONTRACT）+ `customer_quote` 接受 | **有雏形**：缺 resource/state/requirements/quote_snapshot |
| 合同 | 无实体；只有 `quote_type=CONTRACT` / `source_kind=CONTRACT` | **确定没有合同实体** |
| 授信 | `customer.credit_limit` / `supplier_profile.credit_line` + `credit_txn/deposit_txn` | **部分**：有额度字段与流水，无"额度版本/方向"实体 |
| 变更计划 | 无 | **确定没有** |
| 公告 | 有 `alert`（内部告警）、`customer_notification`（客户通知） | **近似但不是**（无"上下架/资源变动/成本变化公告"） |

## 二、订正后的覆盖度结论

| 类别 | 内容 |
|---|---|
| **可直接复用/微调** | 标准模型（SKU/家族）、供应商报价主体、价目表、客户主体与销售归属、审计日志、登录鉴权 |
| **需扩展** | 申报（model_application 扩多行/URL/系数/版本）、客户开通（customer_price_book 扩 resource/state）、授信（credit_limit 扩方向/版本/记录） |
| **确定没有（新增）** | resource 聚合实体、办理流程、客户创建/详情、合同实体、变更计划、公告、测试、自动拉取、按实体的操作记录 |
| **下线（加开关）** | 成本四因子/成本机会/对比、定价策略、变更单/审批、汇率锁、客户门户、供应商报价审批动作、特价/刷新、涨价传导 |

> 相比上一版，**"缺失"从 8 个域缩小到 6 个左右**；"可复用"从 3 个增加到 6 个。
> 但"resource / 办理流程 / 客户创建详情 / 合同 / 计划公告"确实是空白。

## 三、接口收敛清单（保留 / 改造 / 下线 / 新增）

### 保留（不动或微调）
- `POST /login`、`POST /logout`
- `GET /models`、`GET /models/options`、`POST /models`、`PUT /models/:id`（补官方资料字段）
- `GET /suppliers`、`GET /suppliers/:id`（补 region/tax/资源数）
- `GET /customers`、`GET /customers/:id/quote-context`、`POST /customers/:id/transfer`
- `POST /customer-quotes`、`GET /customer-quotes/:id/export`（补系数/毛利字段）
- `GET /audit-logs`、`GET /audit-logs/export`
- `GET /workbench/todos`、`GET /workbench/metrics`（换待办口径）
- 开放接口 7 条（价格/成本类随模块下线）

### 改造（保留接口，改语义/字段）
- 供应商报价：`POST /quotes`、`GET /quotes/history`、`GET /quotes/:id`、`POST /quotes/:id/withdraw`
  → 去审批、补供方名/URL/Key/系数/参与测试
- `POST /model-applications`、`GET /model-applications` → 扩成"申报"（多行/版本/测试）
- `POST /customer-quotes` → 补 coefficient/margin/sale_coefficient/discount
- `customer_price_book` 相关 → 扩成"客户开通"（resource/state/requirements）
- `credit_limit` → 扩成授信记录（方向/版本）

### 下线（加开关、不挂路由、代码和表保留）
- 审批/变更单：`/approvals/:id/decision`、`/change-requests*`、`/model-applications/:id/decision`
- 成本四因子：`/cost/baselines*`、`/cost/params*`、`/cost/baselines/:sku/lock-primary`、`/cost/opportunities`、`/cost/baselines/:sku/compare`
- 旧官方价同步：`/price-sync/jobs*`、`/staging-prices*`
- 定价策略：`/pricing/policies*`
- 涨价传导：`/price-upconduction*`
- 供应商报价审批/异常/追溯：`/quotes/pending`、`/activate-due`、`/:id/diff`、`/approve`、`/reject`、`/expiring`、`/scan`、`/anomalies`、`/retro-effective`、`/:id/confirm-remove`
- 客户报价特价/刷新：`/customer-quotes/:id/special-price`、`/refresh`
- 财务：`/finance/fx-rates`、`/accounts*`、`/fx-lock*`
- 客户门户 7 条
- 组织权限角色写：`/org-permissions/staff/:id/roles*`（角色休眠）

### 新增（主流程）
- resource：列表/详情/增改/状态操作
- 办理流程：flow/node/batch + 办理人
- 客户：创建/详情
- 客户开通：link 创建/状态/历史
- 合同：contract 实体
- 计划/公告：plan/notice/notice_read
- 操作记录：按 entity_type/entity_id 查询（operation_log）
- 测试/自动拉取（后续）

## 四、建议的施工顺序

1. **加 feature flag，先关"下线"组**（路由不挂、菜单隐藏），代码/表不删。
2. **补主流程的"扩展"**：申报（model_application→多行）、客户开通（customer_price_book→resource/state）、报价补系数/毛利。
3. **补"确定没有"的空白**：resource、办理流程、客户创建/详情、合同、计划公告、operation_log 查询。
4. **最后**接测试平台与自动拉取。

---

## 五、一句话

**现有接口不是"不够多"，而是"部分能复用、部分要扩、少数确实空白"。**
你点的几处（SKU=标准模型、供应商报价、价目表、model_application）都对——先把能复用的复用起来，
再把 resource / 办理 / 合同 / 客户创建这些真空白补上，比推倒重来省得多。
