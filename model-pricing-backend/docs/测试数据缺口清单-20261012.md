## 4. 造数方式分类

### A. 纯 HTTP 可造（推荐，零手工插库）

- 供应商提交报价 → `POST /api/supplier/quotes`（带 `Idempotency-Key`）→ 补齐 P0①，
  一步到位产生 APPROVING 单 + `todo_task` + 待审批列表数据。**建议优先做这条。**
- 供应商提交接入申请 → `POST /api/supplier/model-applications` → 补齐 P0③。
- 价目表发布 → `POST /api/internal/price-books/{id}/publish`（2 份 DRAFT 可用）
  → 产生 PRICING_OP → FINANCE 两步审批，补齐 §3.3 的"第 3 步"现场。
- 汇率锁定 → `POST /api/internal/finance/fx-lock` → 补齐 P1 汇率。
- 客户特价申请 → `POST /api/internal/customer-quotes/{id}/special-price` → 补 PENDING 特价。
- 跑扫描 → `POST /api/internal/quotes/scan` → 触发到期/异常告警。

### B. 只能手工插库（后端无写入接口，必须在报告里显式声明）

- `credit_txn` / `deposit_txn` / 账单 `bills`：无任何写入路由，财务侧数据只能插库或等真实计费链路。
- 「即将到期报价」：需要 `valid_to` 落在预警窗口内，要么插库改时间，要么等真实到期。

### C. 不能靠造数解决

- 变更单 `CONFIRMING` / `APPROVING`：先做产品裁决，再谈数据。
- 行级数据域反例数据：本质是主数据体量问题，需要新增供应商/客户/员工并做归属分配（属 B 类）。
