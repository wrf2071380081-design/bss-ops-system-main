## 1. 目标与裁决

`OPS_ADMIN` 在 `000007_seed` 里被授予 `M11`（组织与权限）的**全部 5 个权限点**（V/E/A/C/P），
即运营管理员**能改权限树**，而需求文档 §1.2 给它的职责是「M1–M9 查看 + 工作台全部」、
数据域 ALL（决策 D34：只读为主）——属实质越权。

裁决（2026-10-09）：需求文档那行是「核心职责概览」、有省略。严格照字面收敛会把
`M10:V` / `M11:V` / `M12:V` 一起砍掉，使运营管理员看不到财务 / 权限 / 审计三个模块。
**故只删写权限（E/A/C/P），保留全部查看权限，数据域不动。**

顺带统一命名：「运营管理员」与「运维管理员」是**同一个角色**（`role.code` 都是 `OPS_ADMIN`），
只是 `000007_seed:44` 写成「运维管理员」、需求文档写成「运营管理员」——命名漂移。

### 4.3 验收 3：访问组织与权限页「能看不能改」— **无法实测，原因如下**

`router.go` 里**搜不到任何 `M11*` 挂载**（全仓后端只有 `pkg/perm/perm.go` 的常量定义）。
组织与权限接口属**批次 5，尚未实现**；前端 `internal.orgPermissions` 路由守卫已配
`M11:V` / `M11:C`，但后端路径 404。

因此本批的收敛是**预防性**的：收掉一个当前无接口可触达、但**批次 5 一实现就会暴露**的越权能力。

可推断的生效路径（供批次 5 验收时照此验）：

- 「能看」：`M11:V` 保留 → 前端 `ORG_PERMISSION_VIEW` 守卫放行、后端 `RequirePerm(M11View)` 放行
- 「不能改」：`M11:C`（配置）已移除 → 前端 `ORG_PERMISSION_CONFIGURE` 守卫挡住配置入口，
  后端 `RequirePerm(M11Config)` 会 403

## 5. ⚠️ 影响面提示（与批次 3a 同一口径）

改的是 `role_permission`，而**会话快照在登录时生成**——已登录会话仍持旧权限集，
**必须重新登录才生效**。

本次做了这个影响的实证（同一账号、不重启后端、只切迁移状态再重新登录）：

- 回滚（`down 1`）后重新登录：`perms` = 16 条，重新出现 `M11:E/A/C/P`
- 再应用（`up 1`）后重新登录：`perms` = 12 条，`M11` 写权限全部消失

→ 既证明快照确实是登录时生成的，也证明本批改动**只对重新登录后的会话生效**。
