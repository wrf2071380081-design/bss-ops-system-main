## 3. 契约定稿（原 PROVISIONAL 三条疑问的答案）

- **organization source**：`org_unit`，只取 `status='ACTIVE'`；树由 `parent_id` 递归，
  `children` 嵌套。**不用 `path`**——库里 path 有脏值（见第 8 节）
- **role DTO**：`role` + `role_permission` + `permission_point` + `role.field_mask`；
  缺失列的处理全部走「留空或可验证推导」，不编造
- **data-scope vocabulary**：`role.data_scope` 原值透传 `SELF` / `DEPT` / `DEPT_SUB` / `ALL`

三个「库里没有的列」的裁决：

- `code`：org_unit 无 code 列 → **用 id 转字符串填充**，即 code 恒等于 id，不是业务编码。
  已在后端 model.go、前端 DTO、契约文档三处写明
- `description`：role 无 description 列 → **恒返回空串**，不编造文案；
  已同步前端（DTO 注释 + 页面 `v-if`）
- `portal`：role 无 portal 列 → 按 `role.code` 推导（SUPPLIER/CUSTOMER/其余→internal），
  **角色 code 常量取 `pkg/perm`**，不写裸字符串；推导规则写进代码注释

其他口径：

- `memberCount`（组织）：**含全部下级**的在职人数，不是直属人数
- `memberCount`（角色）：`role_grant` 里**未过期**授权数（`expires_at IS NULL OR > now()`），
  与登录时能否拿到该角色同口径
- `fieldRestrictions`：`role.field_mask` 的 `{"hide":[...]}` 元素，元素是**字段名**
  （如 `unit_cost`），不是可读文案；NULL → `[]`
- `permissions` / `fieldRestrictions` **恒为非 null 数组**，前端可直接 `.length`

## 5. 单测与变异验证

新增用例：`internal/domain/orgperm` 14 个、`internal/repo` 7 个、`internal/api` 1 个。

覆盖要点：

- 三层树的 memberCount 累加（父 10 = 1+2+3+4）
- 孤儿父节点 / 自引用父节点 → 降为根，不死循环、不丢数据
- **子节点排在父节点之前时仍能正确挂载**（防「边遍历边值拷贝」的实现 bug 回归）
- 负责人姓名**一次 IN 查询**取回（3 节点 2 个指向同一负责人 → 只发 1 次、id 去重为 [11]）
- 空数据返回 `[]` 而非 null；仓储错误原样上抛不被吞
- unit_type 映射（COMPANY/DEPT→DEPARTMENT/TEAM/未知兜底）
- 角色字段全量装配、portal 推导、hide 解析、NULL→`[]`、无授权→0
- 权限点排序按 perm.All() 顺序；输出的 code 全部在 `perm.All()` 内
- DryRun SQL：ACTIVE 过滤、GROUP BY、不 SELECT path、不出现 password/token/role_snapshot
- 挂载点钉子：两条路由挂 `perm.M11View`；router.go 内不得出现 `perm.M11Edit/Approve/Config/Privilege`

变异验证（改坏 → 测试必须抓 → 还原 → md5 一致）：

- M1 路由挂载点 `M11:V` → `M11:E` ⇒ **CAUGHT**（`TestRouterOrgPermissionMountPoints`）
- M2 `unitTypeOf` 把 TEAM 丢进兜底 ⇒ **CAUGHT**
  （首轮 **MISSED**：树用例只断言了 DEPT→DEPARTMENT，没断言 TEAM；
  已补 `Type == OrgTypeTeam` 断言后抓回）
- M3 组织树去掉 `status='ACTIVE'` 过滤 ⇒ **CAUGHT**

三个文件还原后 md5 与改动前逐字节一致。

## 8. 偏差与遗留（需要裁决 / 后续处理）

1. **任务书验收 2 的前提与真库不符（已偏离，需裁决）**
   任务书写「换一个没有 `M11:V` 的账号（如 `buyer_a`），两个接口返回 403」。
   真库实测：**`M11:V` 授予了 9 个角色**，含 `PROCUREMENT` 和 `SALES`——
   `buyer_a` 实际返回 **200**。所以 403 反例改用临时账号 `tmp_b5_nom11`（仅持 M1:V）验证。
   **是否要把 M11:V 收敛到管理员类角色**（否则销售/采购也能看到全系统权限矩阵与字段剔除清单），
   属权限设计问题，本批没动，已在 CLAUDE.md 登记待裁决。

2. **`org_unit.path` 存在脏值**：id=2 的 path 是 `/1/1/`，按物化路径应为 `/1/2/`。
   所以本批建树改用 `parent_id`（外键，可信）。脏数据本身未修（属数据治理，
   且 000007 之后 `平台部` 是手工插入的测试数据，不在迁移里）——**建议单独开一批清理**。

3. **`description` 恒空串**：role 表无该列，按任务书「不要编造」返回空串。
   若希望页面有角色说明文案，需要新增 `role.description` 列（新迁移）或前端维护文案表。

4. **`code` 等于 `id`**：组织表无业务编码列。若运营需要真正的组织编号，需加列。

5. **组织树不含成员清单 / 岗位 / 人员分配**——任务书明确「本批只做只读基础版」，
   页面已用 `el-alert` 提示接口未开放。

6. **M11 写操作仍未实现**：`M11:E/A/C/P` 在 router 里零挂载（有测试钉住）。
   目前只有 `PLATFORM_ADMIN` 持有这 4 点（批次 3b 收敛结果），但没有任何入口能用。
