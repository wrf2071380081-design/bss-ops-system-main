## 1. 关键裁决与口径

1. **权限两层不能单删**。M11:E 是权限点，PLATFORM_ADMIN 是角色。若将来把 M11:E 授给别的角色，第二层仍按角色 code 拦住；若中间件被绕过，服务层兜底。与批次 3a「成本参数 M5:C + 服务层 PRICING_OP」同一纪律。

2. **不做行级数据域过滤**。账号管理是全系统管理职能，没有「谁的员工」归属概念，`DataScope` 对它无意义。

3. **单事务**。建人 = `internal_staff` + `account` + `role_grant` + `audit_log` 四连写，事务边界在 repo（红线 8）。

4. **bcrypt cost 10** 落库，审计里只记「口令已重置」，绝不记明文或密文。

5. **最后一个 PLATFORM_ADMIN 保护**：不允许回收唯一平台管理员角色、不允许停用唯一平台管理员，否则平台无人可管（不可逆事故）。

6. **role_mutex 必须拦**：授权前对候选角色 + 已持角色做两两互斥比对（SALES↔PRICING_OP、SALES↔PROCUREMENT）。

7. **外部门户角色（SUPPLIER/CUSTOMER）不允许在此授予**——它们的 owner 是 subject_operator，不是 internal_staff，必须走各自入驻流程。

8. **建人不回查**：`CreateStaffTx` 事务提交后**不**再 `FindStaff` 回查，而是用入参 + 新 id 在内存组装回显——避免「事务已提交、回显却 500」的幽灵成功。

## 2. 踩过的坑（教训沉淀）

1. **GORM 裸 `Select/Scan` 必须显式 `.Table(...)`**：`staffOrgRow` 没配 `TableName()`，GORM 按结构体名推成 `staff_org_rows` → `relation does not exist` → 接口 500。**编译期发现不了，只有真库调用才暴露**，已加 DryRun SQL 断言钉住表名。

2. **`go build | head` 会掩盖 go build 的真实退出码**：`0xc0000409` 崩溃时 `head` 仍返回 0，重试循环第一次就 break，产出旧二进制，导致「修了代码但跑的是旧逻辑」。**判断构建成功必须看 `go build` 自身退出码，不能管道接 head**。

3. **幂等中间件的语义去重 vs 服务层重复校验**：两次 body 完全相同的写请求会被幂等中间件按 biz_key 去重、直接重放首次结果，服务层的「重复授权/重复回收」校验只在 body 不同时才触发。这不是 bug，是幂等的正确语义——但 E2E 断言必须用不同 body 才能打到服务层。

4. **DELETE 无 body 时，测试脚本别把幂等键当位置参数传**：`call("DELETE", path, ADMIN, key)` 会把 key 当 body，导致请求没带幂等键、被中间件 400「参数校验失败」。

5. **迁移 down 必须删 login_session**：`login_session.account_id` 有外键指向 `account`，有会话残留必然报错并让 `schema_migrations.dirty` 置真（`migrate force` 才能恢复）。000027 的 down 就埋了这个雷。
