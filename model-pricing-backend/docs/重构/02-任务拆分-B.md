# 02 · 申报办理与测试（B）

> 对应功能：F5 申报多行、F6 办理流程、F7 测试平台对接、F8 供应商门户**接口**（页面由 A 做）。
> 原型视图：`81/82/83 供应商申报`、`84/85 供应商模型管理`、`86/87 账户设置`、`40/41 供应商报价`、`51/52 供应商详情`。
> 测试平台：`开放接口对接说明（open-api v1）`。
>
> **本轮不动工作台/标准模型库/模型广场**；先做后续模块（申报/办理/测试）的后端契约与数据准备，等产品微调后接 UI。

## 一、范围

### 做
- 申报：多行、草稿、提交、撤回、版本、参与测试。
- 办理：6 节点流程 + 办理人 + 状态推进。
- 测试：供应商触发 → 调测试平台 → 轮询/回调 → 报告入库。
- 供应商门户**接口**：申报、模型管理、账户设置（页面由 A 做）。

### 不做
- 标准模型/供应来源的维护（A，但 C 要用 resource 契约）。
- 客户/报价（C）。
- 审批（本版没有）。

## 二、数据模型（全部用 000033 新表）

- `submission`：supplier_id、kind(SUPPLIER_NEW/MODEL_NEW/PRICE_CHANGE)、region、status(DRAFT/PROCESSING/COMPLETED/WITHDRAWN)、reason、submitted_by/at。
- `submission_row`：submission_id、standard_model_id→`standard_model.id`、supplier_model_name、test_base_url、test_api_key_enc、coefficient、participate_test、test_job_id、test_report_id、row_status、resource_id。
- `submission_version`：版本快照。
- `onboarding_flow`：kind(SUPPLIER/CUSTOMER)、owner_id、status、current_node。
- `onboarding_node`：flow_id、node_key(PREP/CONFIG/TEST/CONTRACT/CREDIT/ACCOUNT/EXECUTE)、status、assignee_id、completed_at。
- `onboarding_batch`：flow_id、supplier_id、models、config_done、status。
- `test_job`：resource_id、category、external_job_id、idempotency_key、status、verdict、request_payload、response_summary。
- `test_report`：test_job_id、resource_id、connection_ms/passed、stress_passed、rps、tps、availability、error_rate、ttft_ms、tpot_ms、sample_count、report_url、tested_at。
- `webhook_event`：event_id 主键、job_id、payload、processed_at。

> 说明：申报用**新表**实现多行；旧 `model_application` **停用**（见 `附02-旧表停用与保留清单.md`），不迁移、不双写。

## 四、业务规则（重点）

### 4.1 多行申报
- 一条 submission 带 N 行；每行：供方模型名、标准模型、URL、Key、采购系数、是否参与测试。
- 提交时：**至少一条**行"连通+压力通过"才允许提交；**连通失败的行不算通过**；其他指标不设阈值。
- 提交后不可编辑，只能先撤回再改。
- 版本：每次提交生成 `submission_version` 快照。

### 4.2 供应商触发测试
- 供应商勾"参与测试" → 点测试 → BSS 调平台 `POST /test-jobs`：
 - `target.model` = 该行的标准模型官方 ID（`official_id`）
 - `target.base_url` / `target.api_key` = 该行的测试凭据（**不是正式接口配置**）
 - `owner` = 供应商
 - `category`：连通用 `health`，压力用 `stress`
 - 带 `Idempotency-Key`（submissionId+rowId+version）
- 平台返回 `job_id`，BSS 存 `test_job`；轮询或等回调更新。
- **正式接口配置与测试凭据分开**：测试只用测试凭据。

### 4.3 回调
- 验 `X-Signature`（HMAC-SHA256，原始 body，±300s）；`event_id` 幂等；落 `webhook_event`。
- 更新 `test_job`（verdict/summary）、`test_report`（指标/报告 URL）。
- 报告保留多条；`resource.latest_test_report_id` 指最新。

### 4.4 办理流程（无审批）
- 节点：账户与接口准备(运营) → 资源配置(运营) → 模型测试(研发) → 合同(商务) → 授信(商务) → 账户开通 → 执行操作。
- 节点只能由 `assignee_id` 完成（绑定式）；完成写 `operation_log`。
- 没有审批节点/审批状态。

### 4.5 状态机
- submission：`DRAFT → PROCESSING → COMPLETED / WITHDRAWN`。
- row：`PENDING_TEST → TESTING → PASSED / FAILED → ADMITTED`。
- node：`WAITING_PREDECESSOR → IN_PROGRESS → DONE`（`DISABLED` 跳过）。
- test_job：`QUEUED → RUNNING → SUCCEEDED/FAILED/ABORTED/CANCELED`。

## 五、验收标准

- 供应商建 3 行申报（不同模型）→ 只测 1 行 → 提交：至少一条通过可提交。
- 3 行全不通过/全连通失败 → 提交被拒（400/409，提示明确）。
- 勾选行的 URL/Key 错误 → 连通失败 → 该行不能算通过。
- 提交后编辑 → 拒绝；撤回后可改。
- 平台回调重复投递 → `event_id` 去重，只处理一次。
- 验签失败/超时间窗 → 拒收。
- 内部完成节点：非办理人 403；办理人 200 且留痕。
- 全流程**没有审批**。
- 测试凭据与正式配置互不覆盖（改一个不影响另一个）。

## 六、依赖与风险

- 依赖 A 的 `resource` 契约（standard_model_id、supplier_id、region、coefficient）。
- 依赖测试平台联调环境（token、回调地址、webhook_secret）。
- 风险：平台回调 at-least-once，必须幂等；报告会归档，BSS 只存摘要+URL。
- 风险：`categories/params` 的字段随门类不同，先只接 `health` + `stress`，其余后续。

## 七、交付物

- 申报/办理/测试接口 + 单测 + 真库 E2E。
- 回调验签与幂等的测试用例（重复投递、错签名、超时）。
- 接口 + 单测；供应商门户页面由 A 负责；内部办理台账页面按分工。
