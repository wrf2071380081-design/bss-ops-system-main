# 04 · 共享契约与前端说明（三人共用）

> 目的：三条线并行开发时，大家按同一套约定写代码，减少联调摩擦。

---

## 一、接口通用约定

### 1.1 响应包（沿用现有）
```json
{ "code": 0, "message": "ok", "data": {}, "requestId": "..." }
```
- `code=0` 成功；非 0 时 `data=null`，`message` 说明原因；参数校验失败带 `errors[]`。
- 错误码沿用：400 参数、401 未认证、403 无权限/非绑定人、404 不存在/模块关闭、409 状态冲突、423 冻结、429 限流。

### 1.2 分页
`?page=1&size=20`，返回 `{list,total,page,size}`；`size` 上限 100。

### 1.3 写操作幂等
所有写接口带 `Idempotency-Key`，沿用现有中间件；同键同 body 返回原结果，异体 409。

### 1.4 金额与精度
- 金额：decimal 字符串，禁 float64。
- 采购系数 `coefficient numeric(8,4)`，范围 (0,1]。
- 毛利 `margin numeric(8,6)`，<1。
- 销售系数 `sale_coefficient numeric(8,4)`。
- 折扣 `discount numeric(6,3)`，0~10。

### 1.5 时间
`timestamptz`，接口 ISO 8601 带时区；展示按 Asia/Shanghai。

## 二、留痕（operation_log）——所有写接口必做

### 2.1 规则
- 每个写接口在**同一事务**里写一条 `operation_log`；业务写成功但日志失败 → 整体回滚。
- `entity_type` / `entity_id` / `action` / `operator_id` / `before` / `after` / `reason` / `request_id`。
- append-only，不 update/delete。

### 2.2 公共 helper（C 来提供）
```go
// 伪代码：由公共模块提供，A/B 直接调用
oplog.Write(tx, oplog.Entry{
 EntityType: "resource", EntityID: id, Action: "STATE_CHANGE",
 OperatorID: staffID, Before: old, After: new, Reason: reason, RequestID: reqID,
})
```

### 2.3 各实体的"操作记录"页
统一查 `GET /api/internal/operation-logs?entityType=&entityId=`，倒序分页。

---

## 三、绑定校验（assertBinding）——所有改操作必做

### 3.1 规则
- 读取：全员可见。
- 写：必须是该实体绑定的那个人。
 - 客户：`owner_sales_operator_id`（销售归属）
 - 资源：`buyer_id`（归属采购）
 - 流程节点：`assignee_id`（办理人）
- 不通过 → 403，文案明确"该记录由 XX 负责"。

### 3.2 公共 helper（C 来提供）
```go
assertBinding(c, entityType, entityID, staffID) // 不通过返回 403
```

---

## 四、平台维度（国内/海外）

- 实体都带 `region`（CN/OVERSEAS）。
- 列表支持 `?region=` 筛选；顶部"全部/国内/海外"切换。
- 校验：报价/开通/申报不能跨区域；客户/供应商主体区域固定后不可改。

---

## 五、模块开关（已实现）

- 配置 `features.*`，中间件 `FeatureGate` 按路由 pattern 拦截，关闭 → 404。
- 前端菜单/路由同步：关闭的模块不显示入口。
- 恢复：`features.xxx: true` 或 `MODEL_BSS_FEATURES_XXX=true`。

## 六、前端改造（按原型）

### 6.1 页面映射
| 原型 | 前端页面 | 负责 |
|---|---|---|
| 工作台 | InternalWorkbench | 公共 |
| 标准模型库 | 新增/改造 | A |
| 模型广场 + 模型详情 | 新增 | A |
| 供应商报价（办理台账） | 改造 | B |
| 供应商管理 + 详情 | 改造 | A |
| 报价单 | 改造 | C |
| 客户管理 + 详情 | 改造 | C |
| 供应商端：申报/模型管理/账户设置 | 改造 | B |
| 客户门户 | 隐藏/删除入口 | C |

### 6.2 交互细节（照原型）
- 列头排序：升/降序，空值末尾。
- 筛选：供应商/公司/类型/部署节点/状态/平台。
- 毛利提示：<3% 弹二次确认（原型是 <30%，**要改**）。
- 报价行：毛利率 ↔ 销售系数双向计算。
- 测试：参与测试勾选；连通失败不可提交。
- 操作记录：每个详情页一个子页。

### 6.3 菜单与开关联动
- 前端从后端拿 feature 状态（或构建时配置），关闭的模块不渲染菜单/路由。
- 客户门户入口移除。

## 七、接口变更流程

1. 先在各自设计文档写"接口草案"（路径/入参/出参/错误码）。
2. 三人评审冻结，写入 OpenAPI/Swagger（`swag` 生成）。
3. 改契约先群里同步，再改代码；禁止先改后通知。
4. 前端按冻结契约做 mock，后端并行实现。

---

## 八、测试与联调

- 单测：业务规则（系数范围、毛利门槛、状态机、绑定 403）。
- 真库 E2E：每条主流程跑一遍，留痕落库。
- 回归：`go test ./...`、gofmt、go vet。
- 联调：A 先交 resource 读接口；B/C 用它做 stub。

---

## 九、分支与提交

- 每人一条 feature 分支（`feature/supply`、`feature/submission`、`feature/trade`）。
- 提交前跑门禁；不跨线改文件；接口契约变更单独提交并说明。
- 不删旧代码/旧表；下线用开关。

---

## 十、文件归属与路由拆分（避免合并冲突）

**目标：三人代码文件零交集。** 详细文件表见 `00-总览.md` §〇.1。

**路由已拆分（2026-10-20）**：
- `internal/api/router_supply.go`（A）
- `internal/api/router_submission.go`（B，含 `registerOpenCallbacks`）
- `internal/api/router_trade.go`（C）
- `router.go` 只保留遗留路由和三个 `registerXxx` 调用；**新路由只加到自己文件**。

**依赖装配**：`cmd/server/main.go` 统一维护；A、B 只新增自己的构造函数，不直接改 `main.go`。

**其它热点文件归属**：
- `migrations/**`：统一维护；A、B 提 schema 变更请求，统一写 000034。
- `openapi/**`（swagger）：统一维护；联调末尾统一 `swag` 重新生成。
- `pkg/oplog`、`pkg/binding`：统一维护；A、B 只调用。
- `internal/infra/config/**`、`configs/**`：统一维护。
- 前端 `src/router/**`、`AppLayout`、公共组件：统一维护；A、B 只改各自 `views/`、`api/`。

**结论**：按上述边界，除"接口契约"需要同步外，**代码文件不会冲突**。
