## 1. 两份来源文档先统一的口径

1. 产品交互基准改为本次Lovable原型，保留原v0.22作为历史参考，不擅自命名新版号。原型虚构价格、测试结论和演示模拟按钮不是生产事实。
2. 不再写“全系统无审批”或“审批中心只对领导显示”。供应商报价审批仍保留，统一在有审批资格领导的工作台待办展示，复用原决策和分派流程。任一具资格人员完成一次共享审批后产生指定人员的执行待办，不改为全员会签或单人独占审批。
3. 普通待办仅绑定人员办理，人员筛选不是身份切换；公告按人员独立已阅；A按具体动作分别校验维护人、采购人、节点办理人或计划原发起人。
4. 只有A/B/C三条工作线。共享文件统一维护不等于另有一位公共负责人；C提供F14日志/绑定工具，A负责自己的安全存储、计划执行、提醒等业务，B负责申报、审批分派/办理与测试事实。认证和共享文件按实际约定协作，不给未点名的人分配依赖。
5. 结构基线更新为现有33–36及其映射；移除“运行库32、等待000033、所有领域属性先补同名列、统一写000034”的当前前提。新需求确需结构时提出具体增量请求，不能改历史迁移或执行旧建议DDL。

## 2. A任务按功能重排

| 功能 | 修订后的A交付 | 修订性质与现有基础 |
|---|---|---|
| F1 标准模型 | 复用八类资料、价格项、来源、缺失提示、版本/日志与维护能力；对齐新版表格、单一维护入口和抓取结果摘要。保存与人工核验的关系确认后调整入口 | 大部分复用，不重做模型仓储；单一保存入口不能直接解释成取消核验 |
| F3 供应来源/广场 | 保留聚合、区间筛选、资源独立报告；按新版详情列导航到供应商及对应模型上下文，补实际上架时间/历史缺失；对接逐行配置完成、确认开通、取消接入和内部改价命令 | 增补运行接线、写流程与导航，B提供来源/报告/办理事实；不让前端自报测试通过 |
| F4 供应商主体池 | 完整供应商列表及四页签详情；税率可空、曾用名查询、主体测试URL/Key、潜在/已有与办理状态两个维度；加入人工合并及旧链接追溯 | 主体池、共享测试配置与合并为实质新增；复用现有主体CRUD、加密与日志。正式生产配置/网站账户是否保留当前入口待确认，不先删代码或盲目继续扩展 |
| F8 供应商门户（A任务范围） | 对齐手机号验证码登录、注册、营业执照及主体规则确认；完成任务书分配给A的门户业务内容，并按契约衔接申报、模型管理、账户资料和主体共享测试配置 | 身份认证、申报、办理和测试等跨模块事实由对应业务模块提供，A不复制这些模块的业务规则；责任按业务模块划分，不按前端/后端拆分。登录后的完整页面需继续核查，不能直接删掉原多草稿/保存保护要求 |
| F12 合同与授信 | 将已有详细设计的名称/编号、版本、当前额度、来源办理、实际办理人和附件写入真正落地；供应商/客户共用资料能力，分别消费B/C上下文 | 多项是原设计已有而未实现，非全部新增需求；当前只读投影保留为查询基础，不能替代写入及readiness |
| F13 计划与公告 | 复用上下架原发起人登记、提醒、个人已阅；补内部调价计划及指定执行人的规则、成本变化公告和停供影响导航；工作台接实际业务对象 | 上下架链路已部分真库验收；调价不能机械套用全部上下架发起人权限。C负责客户关系事实与影响处理 |
| F2 官方抓取 | 保留规则/抽取/差异确认和价格不静默覆盖；展示尝试/成功/失败分离 | 继续阶段3增强，不阻塞手工业务主流程，不把模拟更新当已交付 |

工作台独立审批中心的菜单和产品入口需收敛，审批API及服务端资格校验保留；旧深链的兼容处理按路由实际情况设计，不在需求中预设一个未经核对的新跳转路径。

## 5. 已确认边界与仍待确认事项

1. **资料保存/核验（已确认并实现）**：按单一“手动补全/保存”操作处理；资料不完整时保存并标明缺失项，完整资料由维护人核对来源和日期后原子保存及核验，修改已核验资料会使新版本回到待核验。报价仍要求当前版本核验通过。实现和定向证据见TDD SUMMARY Stage76。
2. **测试/正式配置（来源和存储决策已确认）**：供应商自测URL/Key使用供应商自己的池子和额度，内部测试使用平台URL/Key与平台额度，两套凭据不混用（DEC-017）；正式配置Key按DEC-018原样保存，不使用AES-GCM，页面/API/日志不回显原文。供应商测试配置由谁持久化、怎样绑定Inspector及真实业务入口仍需B提供接口事实；正式配置权限、引用停用保护、资源绑定/接入前置按F4契约继续执行，不再把是否移除AES加密列为待确认。
3. **内部改价与分派**：与供应商申报审批的关系、允许创建/指派人员、是否由指定执行人实际完成、约定时间仅提醒还是其他行为；不能自动触发生产变更或套用上下架created_by策略。
4. **主体生命周期/合并**：有过上架历史的准确判定、潜在转已有条件、上架前已有申报/合同的区域修改、跨区域归并和引用冲突的处理。A/B/C据此共同保证事实一致。

合同授信的资料名称/编号/版本、2MiB、额度不累加等已有设计应保留为基线；新增表单未显示某个限制不代表规则已取消。若产品明确不同，再按独立差异修订；供应商审批入口合并已经确认，无需重问审批是否存在。
