## 业务、授权与HTTP

### 目标和责任

F12 由 A 维护一套供应商、客户共用的合同与授信资料能力。主体身份始终使用 `(subject_type, subject_id)`：供应商对应 `supplier.id`，客户对应 `customer_profile.id`。客户新增、编辑、销售归属、客户合并、资源开通和报价仍由 C 负责；A 提供 F12 面板、API、主体校验适配和资料业务规则。

供应商、客户页面复用`F12SubjectPanel.vue`。正式F12迁移编号为v44，日常库已45/false；Stage200曾用本地43编号，现已对齐，见[升级说明](./database-v45-upgrade.md)。v36/42兼容读取保留，缺F12实际结构或附件配置仍关闭写入，不把旧`file_ref`当成`file_id`。

### 当前供应商运行接点

- `NativeSupplierF12`读取真实SUPPLIER onboarding_flow、CONTRACT节点及原生APPROVE关联，来源revision沿既有契约取不可变批准日志ID；同时核对申报、主体、当前节点、实际办理人及expected版本。首次未办结时，普通采购人不能绕过节点写资料。
- 指定商务办理人可在CONFIG进行时准备资料（WAITING_PREDECESSOR），但登记完成必须等CONFIG COMPLETED、CONTRACT IN_PROGRESS且当前资料齐备。每个最新合同/授信版本须来自同一主体、flow/module和批准版本，要求合同及供应商结算币种的授信；不接受浏览器自报ready或资料ID。
- `F12ReadTransactions`在完成HTTP中借用同一公共SQL事务，普通GET保持只读快照。资料齐备事件通过`readiness-change`反馈办理面板，资料缺失/加载失败不启用完成按钮。最终完成保存节点、流程、申报及精确资料版本日志，再由工作台显示已办。
- 流程写入只属于实际指定人；附件读取允许当前指定人或真实归属链上的当前采购人，采购人读取不获得代办权。读取授权不使用FOR SHARE，兼容附件下载的只读事务。
- 运行配置与备份见[附件部署说明](./f4-f12-file-persistence-deployment.md)。

### 资料类型和版本规则

#### 合同

- 一份合同档案有稳定 `contract_key`；每次新增或修订追加一条版本记录，不覆盖旧版名称、编号、说明或附件。
- 新版本至少包含资料名称、资料编号、明确主体、版本号、状态、附件 `file_id`、保存人和创建时间；可选来源流程、来源模块、实际办理人及原因。
- 合同状态使用 `PROCESSING` / `ARCHIVED`。归档是业务完成登记，不新增审批；归档不得改写合同正文或历史附件。普通维护归档按主体责任人授权并清除归档版本的旧流程来源；若归档发生在首次商务办理中，必须携带对应的流程/模块和 expected revision，经 B/C 事务授权后将实际授权 revision 写入归档版本。
- 同一合同档案的版本唯一。主体可以有多份合同档案。
- 合同金额不自动更改授信。

#### 授信

- 供应商方向固定为 `SUPPLIER_TO_US`，客户方向固定为 `US_TO_CUSTOMER`。
- 授信版本维度为 `(subject_type, subject_id, direction, currency)`；每次调整追加新版本。
- 金额必须大于零，使用精确十进制字符串；零、负值、超精度或非数字拒绝。
- 当前额度取该维度最新成功保存的版本，不累加历史。历史最高版本有多条且无法判定时，返回冲突状态，不任意挑一条。
- 币种显式保存。币种不同的额度不相加。

### 首次办理与普通维护授权

- 首次接入所需合同/授信资料，只能由 B/C 提供的可信流程事实授权对应商务模块办理人上传。A 重新读取主体、流程、模块、办理人、版本和状态并服务端校验，不信任客户端传入的 `can_upload`、`operator_id`、`source_flow_revision` 或完成状态。流程写入请求另带 `expected_flow_revision` 作为客户端看到的 CAS 比较值；提供方必须在同一事务中比较，实际写入的 `source_flow_revision` 仍只能采用提供方在事务中读取的真实值。
- 首次商务模块资料可与运营模块并行办理；上传成功不代表另一模块完成，也不由 A 推进 B/C 流程。
- 整体首次商务办理结束后，后续资料维护使用项目确认的主体绑定/操作授权。授权来源缺失或不明确时拒绝写入并保持只读。
- 每次成功写入将资料版本和 `operation_log` 同事务提交；流程来源版本由同事务授权器返回并保存，不接受客户端填值；幂等重放不重复创建版本。旧版本、附件和操作人快照保留。
- 流程资料列表同时显示来源流程、模块和服务端保存的流程修订号。当前办理人由提供方在写事务核实为认证操作者后，`created_by` 保存该操作者；页面仅在来源上下文完整且修订号有效时，将该可信 `created_by` 映射为“实际办理人 ID”。普通维护只显示“登记人 ID”，不伪称为流程办理人。说明列展示该版本的 `reason`，旧结构缺失时显示“未记录”。人员姓名需共享人员目录提供；该目录未接入前显示经过校验的内部员工 ID，不编造姓名。

### 附件

- 当前仓库没有可复用 D07 文件提供方，A 提供一个最小私有附件适配器并生成 opaque `file_id`；后续如 D07 提供稳定接口，可按此端口替换。文件先上传，再把 `file_id` 绑定到具体主体及合同/授信资料版本。
- 单文件最大 2 MiB（2,097,152 字节），超过 1 字节拒绝；文件类型服从共享文件服务白名单。
- 更新时可明确沿用同一档案上一版本附件；不能引用其他主体或其他资料档案的附件。首次创建必须带合法附件。
- 列表及普通 API 不返回物理路径、存储 URL 或供应商密钥。下载每次重新校验操作者、主体、资料档案和文件用途。
- 下载按已引用该文件的记录重新授权：普通维护只允许当前主体责任人；带来源流程的记录必须通过 B/C 当前办理人事实校验。没有流程授权提供方时，流程记录附件下载 fail-closed；不能因员工账号有效或知道文件 ID 就放行。
- 文件上传、版本保存和失败重试按共享附件服务契约处理；不能在 SQL 事务中进行网络文件传输。

### API 草案

- `GET /api/internal/contracts?subject_type=SUPPLIER|CUSTOMER&subject_id=...`：按主体读取合同资料和历史版本。
- 合同列表可附加`contract_key`限定单一档案；`latest_only=true`必须同时指定合法`contract_key`。最新版本按同主体类型/ID/档案的最大version读取，不依据当前页面或created_at，返回标准分页包络。重复最高版本返回409，缺少档案键结构返回503，不伪装成无记录。普通历史读取不要求新增结构，保持旧投影兼容。
- `POST /api/internal/contracts`：创建合同档案首版本；首次流程资料带 `source_flow_id`、`source_module_key` 和 `expected_flow_revision`，普通维护省略流程字段。
- `POST /api/internal/contracts/:contractKey/versions`：追加合同版本，带 `expected_latest_version` 和幂等键；流程办理修订另带相同的来源上下文及流程 CAS 值。
- `POST /api/internal/contracts/:contractKey/archive`：归档当前档案，带预期版本和原因；首次商务办理内归档另带 `source_flow_id`、`source_module_key` 和 `expected_flow_revision`。
- `GET /api/internal/credits?subject_type=...&subject_id=...`：读取授信历史和当前额度。
- `GET /api/internal/f12/readiness?subject_type=...&subject_id=...&flow_id=...&module_key=...`：根据可信 B/C 流程模板及 A 当前合同/授信版本，返回精确版本引用、金额/币种、`ready` 与 `missing_reasons`。流程模板和所需资料项只由服务端提供方决定，不能由调用端提交。
- `POST /api/internal/credits`：追加授信版本，带方向、币种、正额度及幂等键；首次流程资料的来源上下文含 `expected_flow_revision`。
- `POST /api/internal/f12/attachments`：上传 2 MiB 以内 PDF/PNG/JPEG，提交主体、用途和原因；流程上传需带来源上下文和 `expected_flow_revision`，普通维护省略，成功返回 opaque 文件 ID。
- `GET /api/internal/f12/attachments/:fileId?subject_type=...&subject_id=...&purpose=...`：仅在文件已被该主体的合同/授信版本引用后下载；核对主体与用途，不返回存储路径。

路径可按项目既有路由规范调整，但必须保留主体类型、稳定档案键、版本、幂等和授权语义。

### 关键失败语义

- 主体不存在、主体类型与方向不匹配、未知流程或文件归属不匹配：拒绝请求，不写资料或日志。流程内归档与其他流程写入一样，授权版本变化返回409；普通归档不会借用旧版本来源冒充流程办理。
- 无首次办理资格：403；流程模块已完成、流程版本变化或档案版本冲突：409。readiness 读取期间流程 revision 或必需项发生变化时返回409。
- 同一幂等键相同请求：返回原结果且不增版；同键不同内容：409。
- 页面收到 409 时，在当前编辑弹窗内显示冲突并保留输入及已上传附件；用户显式刷新后重读最新合同/授信版本、更新 CAS 版本并创建新的幂等生命周期，再由用户确认重试。首次办理若流程 CAS 冲突，面板发出 `refresh-flow-context` 事件；嵌入工作流的一方须重新读取可信流程上下文并传回新 revision，收到新上下文前禁止重试。普通主体页面不存在流程上下文时只刷新主体资料。
- 合同修订/归档冲突刷新调用上述按档案最新版本查询，不能只在当前20条历史中查找。修订表单展示服务器最新名称、编号、版本及附件状态作核对，保留草稿和已上传文件；未选新文件则使用刷新后的本档案附件。档案已归档、查询失败、主体/档案错配或版本重复时禁止重试。首次办理还需收到真实新流程revision；仅刷新流程上下文不能绕过合同最新版本核对。本轮实现为源码/前端纯函数检查状态，HTTP/SQL及真实页面待Docker恢复后验证。
- 日志写入失败：资料版本整体回滚。
- 历史遗留记录缺名称/编号/文件信息时，安全展示可用旧字段并标明历史资料；不补造缺失信息，不将其作为本次首次办理资料满足条件的证据。

### 页面验收

供应商和客户共用相同面板，分别显示资料列表、名称/编号、类型、状态、版本、金额/币种、登记人与可信流程办理人、来源、时间、说明、附件操作及历史。供应商与客户即使数字 ID 相同也不得串数据。每种主体至少完成一次真实新增、刷新重载、修订、查看旧版和授权下载；另验证主体/办理人权限、冲突、幂等和附件大小边界。只读兼容面板不计作写入验收。

## 正式v44字段、约束与兼容

### 正式字段与约束

#### `contract`

在保留旧列兼容读取的基础上，请增加或提供等价映射。现有 `contract.version` 已是非空 integer；A 建议直接复用为合同档案内的业务版本，不额外增加 `version_no`。迁移维护人若发现旧数据或写入兼容性不允许复用，再说明原因并提出等价结构：

| 字段 | 用途与规则 |
|---|---|
| `contract_key` | `text` 稳定合同档案标识；同一合同各版本共享，主体可有多份合同；旧行保持 NULL，新写入必填 |
| `document_name` | `text` 资料名称；旧行允许 NULL，新写入必填 |
| `document_no` | `text` 资料编号；旧行允许 NULL，新写入必填 |
| 复用 `version` | 不可变业务版本，按 `contract_key` 递增；不另增重复版本列 |
| `file_id` | `text` 受控附件标识；不等价于旧 `file_ref`；旧行允许 NULL，新写入必填 |
| `source_flow_id` | `text` 首次商务办理来源，可空于普通维护 |
| `source_module_key` | `text` 例如合同商务模块的来源标识，可空于普通维护 |
| `source_flow_revision` | `bigint` 服务端事务内读取的可信来源版本；流程记录必填，普通维护为NULL。当前原生供应商用实际APPROVE日志ID，HTTP expected值仅作CAS，不能冒充事实 |
| `reason` | `text` 本次新增/修订/归档原因；历史行允许 NULL，新写入必填 |
| `created_by` | `bigint` 认证操作人；旧行允许 NULL，新写入必填 |
| CAS | 复用`expected_latest_version`校验当前档案版本，不增加重复revision列 |

要求合同版本按新行追加，旧版内容及附件保留；建议使用 `WHERE contract_key IS NOT NULL` 的部分唯一索引 `(contract_key, version)`，保留没有稳定档案键的历史行。`PROCESSING/ARCHIVED` 为业务状态，归档不得改写历史内容。保留 `subject_type/subject_id` 作为每次读取、授权和下载的隔离维度。

#### `credit_line`

在保留旧列兼容读取的基础上，请增加或提供等价映射：

| 字段 | 用途与规则 |
|---|---|
| `document_name` | `text` 授信资料名称；旧行允许 NULL，新版本必填 |
| `document_no` | `text` 授信资料编号；旧行允许 NULL，新版本必填 |
| `file_id` | `text` 受控附件标识，不等价于旧 `file_ref`；旧行允许 NULL，新版本必填 |
| `source_flow_id` / `source_module_key` | `text` 可信办理来源，可空于普通维护 |
| `source_flow_revision` | `bigint`，同合同的可信来源版本；当前服务保留既有正数及MaxInt32输入边界，不把客户端expected值直接存为事实 |
| `reason` | `text` 新增额度版本的业务说明；旧行允许 NULL，新版本必填 |
| `created_by` | `bigint` 认证操作人；旧行允许 NULL，新版本必填 |
| 复用 `version` | 同主体、方向、币种下递增的业务版本；不另增重复版本列 |

约束为 `(subject_type, subject_id, direction, currency, version)` 唯一；新版本 `amount > 0`。方向只允许 `SUPPLIER_TO_US` 对应 `SUPPLIER`、`US_TO_CUSTOMER` 对应 `CUSTOMER`。授信新版本追加，不覆盖历史；当前额度取最高成功版本且不累加。

### 历史兼容与安全迁移

1. 迁移前检查真实运行库版本、`contract` / `credit_line` 行数、最大版本重复、已存在字段和索引；不能仅凭仓库迁移文件推断运行状态。
2. 旧合同每行可映射为独立 `legacy:<id>` 档案或使用等价稳定键；保留旧 `version`、状态、时间及 `file_ref` 原值。缺失的名称、编号、受控附件 `file_id`、流程、人名保持缺失并标为历史，不伪造。
3. 旧授信保留原主体、金额、币种、生效时间、版本与 note；不重新排序、不累计金额、不把旧 note 解释成资料字段。
4. 若历史最大版本存在重复，迁移不得删除或任选一行。需保留现有读取的歧义状态，同时为新写入建立可证明的唯一递增版本约束；迁移实现人先提交预检结果及可回退映射。
5. 新旧 API 并存期间，旧只读查询继续工作；新写入口只在新结构、文件提供方和授权上下文全部装配后开放。
6. DDL 必须提供明确 down/回退策略。不能在 A 的页面/API代码中隐式触发生产迁移。

### 同事务和索引要求

- 新版记录写入、版本分配/锁、`operation_log` 和共享幂等结果必须满足现有公共事务约定。日志失败时业务写整体回滚。
- 建立主体类型/主体 ID/状态/版本的查询索引及上述版本唯一约束；优先复用现有 integer `version`，为旧数据保留只读路径。
- FK 指向 `supplier` 或 `customer_profile` 的多态关系不能靠单一普通外键表达，必须由 A 的 SubjectReader 在同一写事务中校验实际主体类型和存在性。
- 来源流程表和 D07 文件表名称/主键尚需由实际提供方核实；请求不预设未确认的外键目标。`source_flow_revision` 必须来自事务内授权结果，用于把合同/授信版本绑定到实际授权时的流程快照，并供后续 readiness 精确追溯；不能把表单参数或响应中的流程版本当作事实。
- 流程写入 HTTP 可接收 `expected_flow_revision`，仅作为客户端 CAS 比较值。B/C 授权适配必须在同一数据库事务中核对该值与当前流程 revision 一致；版本已变化返回409。实际存入 `source_flow_revision` 的仍必须是授权适配从可信流程事实读取的当前值。附件下载使用独立读取授权端口，不接受写操作的 CAS 值。

### 责任与交接（Stage205更新）

## 旧表只读兼容投影

### 现有结构投影

- 合同返回主体、记录 ID、状态、原生 `version`、签署时间、创建/更新时间及 `has_attachment`。不得返回 `file_ref` 或 `note`；`has_attachment` 只表示旧记录存在非空附件引用，不代表可下载或引用有效。
- v36 `contract` 是单行记录并原位更新，没有稳定合同档案键和不可变历史表；因此不得把 `version` 展示为可浏览的版本历史。资料名称、资料编号、来源流程、附件 ID 均不在响应中伪造。
- 授信历史返回主体、记录 ID、方向、币种、金额字符串、原生 `version`、生效/创建时间。列表顺序只用于展示，不决定当前值。
- 当前授信按主体、方向、币种分别选原生最大 `version`。同一维度最大版本有多行时，返回 `AMBIGUOUS_VERSION` 且不返回金额；最大版本金额非正时返回 `INVALID_LEGACY_AMOUNT` 且不作为有效当前额度。没有记录时当前额度列表为空，页面显示“未登记”，不显示 0。
- 显式 `as_of` 以 `created_at <= as_of` 限定候选记录，再按原生最大版本计算；它只用于兼容数据查询，不能补足 v36 缺失的不可变版本保证。

### API

- `GET /api/internal/contracts?subject_type=SUPPLIER|CUSTOMER&subject_id=...&status=...&page=...&size=...`
- `GET /api/internal/credits?subject_type=SUPPLIER|CUSTOMER&subject_id=...&direction=...&currency=...&as_of=RFC3339&page=...&size=...`
- `SUPPLIER` 只接受 `SUPPLIER_TO_US` 方向；`CUSTOMER` 只接受 `US_TO_CUSTOMER` 方向。每次读取同时按主体类型与 ID 过滤，不能只用数字 ID。
- 两个入口只允许内部员工身份；主体必须存在。未知/重复查询字段、非法主体、方向、币种、时间或分页参数返回 400。
- 响应提供分页列表和当前授信投影。读取不写操作日志，不自动完成流程。

供应商身份使用supplier.id，客户使用customer_profile.id；不得假设与customer.id或其他同数字ID相等。旧字段兼容读取不表示新写入口只读；实际结构能力检查、权威授权和附件目录未满足时写入关闭。正式编号及旧本机编号区别见[升级说明](./database-v45-upgrade.md)。
