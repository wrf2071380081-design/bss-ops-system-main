# A 模块决策记录

本文件记录用户已明确的选择及其边界。需求和草案仍分别见原始任务材料与模块契约；未列为已确认的建议不能视为用户已批准。

当前业务需求汇总见[2026-10-21需求结论与规划](./2026-10-21-requirements-and-plan.md)。早期记录中的全系统无审批口径不再适用；以下新增决策明确本轮覆盖范围。

## DEC-001：公共基座与 A 的责任边界

- 日期：2026-10-20。
- 状态：用户已确认。
- 选择：先做 A 的契约和独立业务代码；与 A 任务无关的公共能力由公共负责人补齐。
- 依据：用户回复“可以先做A的契约和独立业务代码。其他的与我任务无关的就由公共负责人补齐”。
- 落地：明确目标 schema、公共装配、事务留痕、绑定及附件/加密依赖；不宣称缺失基座已完成，不以旧业务表或同义临时表替代新表。

## DEC-002：逐资源测试准入

- 日期：2026-10-20。
- 状态：用户已确认。
- 选择：每个资源必须自己的连通性和压力测试都通过，才能登记接入并供报价使用。
- 批次规则：整批申报至少一条通过的提交门槛，不自动赋予其他行接入资格。
- A/B 契约：B 提供对应申报行/目标版本的连通性和压力结论；A 在登记接入时验证自身证据适用性。不能把一个模型的测试结果当作同批其他模型的结果。
- A/C 契约：资源可报价结果必须包含该资源当前有效的测试依据；批次 ID 或批次通过布尔值不能代替逐资源依据。
- 验收：三行仅一行通过时可提交整批；只有该行对应资源可在其他前置满足后接入，另外两行被阻断，且失败不产生成功状态/日志。
- 尚未由本决策确定：测试有效期、测试目标变化判定细则以及已接入资源复测失败的处理。资源创建时机见 DEC-003；不得据此自行增加时效阈值或自动下架规则。

## DEC-003：申报与资源创建时点

- 日期：2026-10-20。
- 状态：用户已确认。
- 选择：申报提交并进入办理后创建 resource；草稿阶段只保留申报行和测试记录。
- B 的测试记录在资源创建前应能关联申报行及其目标版本，不要求草稿先有 resource_id。
- 进入办理时，通过 A 的统一资源创建能力，以 supplier/model/region 及来源申报行防重；根据该行有效测试证据决定待测试或待接入。
- 资源创建不等于接入成功，不使供应商 established 自动变为 true，也不使资源自动可报价。
- B 调用 A 及行 resource_id 回写应共享事务，失败不得出现只有一方完成。
- 尚待核对：目标 DDL 的行/版本关联字段、B 的事务适配签名及申报重试的正式幂等契约。

## DEC-004：标准模型不完整资料可保存

- 日期：2026-10-20。
- 状态：用户已确认。
- 选择：允许将八类资料尚未补齐的标准模型保存为待补齐资料，明确列出缺失项；补齐且人工核验后才可报价。
- 保存时仍须校验已提供字段的结构和数值合法性；业务资料缺失不等于可以接受非法价格、重复价格项或错误字段类型。
- `missing_fields` 用于定位待补资料；`quote_readiness` 必须阻断缺失资料和未核验模型。
- 不将保存成功、字段齐全或日期已填写视为人工核验成功；缺失价格与有效零价格保持区分。

## DEC-005：标准模型初始维护人

- 日期：2026-10-20。
- 状态：用户已确认。
- 选择：新模型自动绑定当前创建者；之后通过公共转交能力更换维护人。
- HTTP 新增请求不允许通过自报 maintainer_id 选择其他维护人，操作者来自内部认证上下文。
- 常规更新不得顺带转交维护人；公共转交能力未接入时，不提供绕过绑定的替代写入口。
- 读取仍遵循内部全员可见口径，不将维护人绑定误用为读取数据域过滤。

## DEC-010：上下架严格沿用原型计划流程

- 日期：2026-10-20。状态：用户明确确认“严格沿用原型”。
- 上下架入口先创建计划，再由原计划发起人登记实际完成。当前资源采购人不因归属变化获得代办计划资格。
- 先前切片新增的直接登记页面和POST resources/:id/state不作为生产入口，已撤下。历史测试报告保留当时事实，但不能作为当前路由/页面说明。

## DEC-011：个人阅读与单人待办

- 日期：2026-10-21。状态：已明确。
- 工作台默认当前人员，按姓名切换只影响查询。进入待阅范围的业务消息面向全部在用内部人员，不因消息业务类型、岗位或审批资格排除；每人可阅读，并独立标记自己的已阅。
- 查看他人的待阅状态或待办时，均不得代替对方写状态。查看待阅内容只允许当前登录人标记自己的已阅；普通执行待办同一时点仅绑定一名办理人，只有绑定人能执行，其他人可查看详情并进入业务页但不得代办或改绑定人。
- 默认筛选本人不等于所有待办都向全员分发。供应商报价审批候选事项仅向有审批资格人员提供，见DEC-012和DEC-015。
- 详情页重查真实登录主体及记录资格，不能用工作台选择人员授权；打开待阅详情不自动已读。

## DEC-012：供应商报价专门审批与后续分派

- 日期：2026-10-21。状态：已明确。
- 不建立岗位高低层级；供应商报价保留专门审批资格。标准模型库和模型广场不新增审批步骤。
- 报价提交后由有资格人员处理共享审批事项，任一人完成即可结束当次审批，不要求全员审批，必须防止重复决策和分派。
- 审批时选择后续办理人，审批和分派完成后才产生对应人员的执行待办。执行当前已绑定任务不重复选择当前办理人，后续交接单独处理。
- 申报、核验和普通业务办理不自动等同领导审批；A消费可信办理/审批结果，不增加另一套审批实现。

## DEC-014：按现有34结构调整详细设计

- 日期：2026-10-21。用户明确采用现有34结构，并授权依据原型和最新需求调整详细设计。
- 不再以新增独立控制列为接入前提；F1元数据使用现有版本快照，资料用现有列，行锁及持久快照revision保证并发检查。
- 保留integer版本范围和官方身份全量唯一约束。不完整资料仍可保存，但相同身份（包括空身份）不绕过数据库唯一条件。
- 不捏造历史行维护人/核验状态；F3逐项复用现有数据及B事实，不把每个领域属性强制转成新增列。完整映射见[33–36基线](./2026-10-21-schema34-baseline.md)。

## DEC-015：首次模型、自测覆盖与审批可见性

- 日期：2026-10-21，按最新业务补充调整。首次双流程以供应商此前是否已有模型判断，与注册/登录解耦；首次可批量提交多个模型，合同授信按适用批次建立。B处理首次并发及未完成前置，A不从浏览器计数猜测。
- 改价由审批人指定本次办理人，在适用配置节点处理，不固定为原测试人或另设改价岗位。
- 提交自测覆盖每个模型的连通性，至少一个模型做压力测试。测试覆盖不等于通过，批次提交不等于逐资源准入；资源自身连通性和压力通过要求继续有效。
- 报价提交者为认证供应商；内部审批人与执行人单独留痕和展示。
- 无审批资格者隐藏审批中心及候选事项，后端仍强制资格校验。普通业务资料读取范围不据此缩小。
