## 2. 实施顺序与理由

```
G1 ─┐
G2 ─┴─→ G4 ─→ G5 ─→ G3 ─→ (G6)
               │      ↑
               └──────┘  G3 的下架联动要读 G4 的绑定状态
```

**为什么这个顺序：**

1. **G1、G2 先做**：纯前端、零后端、互不依赖，可以马上出可见成果，也顺手把「详情页 4 Tab 的壳」摸清楚（G5 要复用同一套）。
2. **G4 在 G5 之前**：没有绑定对象，客户详情「接入模型」就是空壳，会返工。
3. **G3 放 G4 之后**：批量下架要提示"影响 N 个客户"，这个数字只能来自绑定表。顺序反了，下架会"提示影响 0 个客户、实际把客户服务打断"。
4. **G6 最后**：动的是合同授信的合规派生字段和附件鉴权链，风险最高、收益最低，且需产品拍板。

### G4 · 客户—模型—来源绑定（约 7~8 人日，**唯一动数据库**）

**表设计：新建 `customer_resource_link`，不复用 `customer_link`**

理由：`customer_link.customer_id` 指向 `customer`（000033），而客户管理全程读 `customer_profile`（000002），两套客户模型没有映射；`customer` / `quote` / `customer_link` 三表在 Go 侧零引用。复用等于先造数据再双写。

```sql
-- migrations/000049_customer_resource_link.up.sql
CREATE TABLE public.customer_resource_link (
  id                  BIGSERIAL PRIMARY KEY,
  customer_profile_id BIGINT NOT NULL REFERENCES public.customer_profile(id),
  standard_model_id   BIGINT NOT NULL,
  resource_id         BIGINT NOT NULL,
  quote_id            BIGINT,              -- 来源报价单，可空（人工登记场景）
  state               TEXT NOT NULL,       -- ACTIVE / DISABLED / DISABLE_PENDING / RESTORE_PENDING / SUPPLY_OFFLINE
  activation_note     TEXT,
  activated_at        TIMESTAMPTZ,
  archived            BOOLEAN NOT NULL DEFAULT FALSE,
  created_by          BIGINT NOT NULL,
  created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  revision            INTEGER NOT NULL DEFAULT 1
);
-- 同客户同资源只能有一条生效绑定
CREATE UNIQUE INDEX uk_crl_customer_resource ON public.customer_resource_link(customer_profile_id, resource_id) WHERE archived = FALSE;
-- 同客户同模型只能有一条生效来源（换来源必须先归档旧的）
CREATE UNIQUE INDEX uk_crl_customer_model ON public.customer_resource_link(customer_profile_id, standard_model_id) WHERE archived = FALSE AND state = 'ACTIVE';
CREATE INDEX idx_crl_resource ON public.customer_resource_link(resource_id);
```

| 子项 | 内容 |
|---|---|
| G4.1 | 迁移 000049 建表 + 两个唯一索引 + 注释 |
| G4.2 | 领域层 `internal/domain/customer/link.go`：状态机（启用→禁用待执行→已禁用→恢复待执行→启用；供应下架→SUPPLY_OFFLINE）、乐观锁 `revision` |
| G4.3 | 读取投影：客户详情「接入模型」按 模型 → 有效可用资源数 / 已绑定资源数 / 服务状态 |
| G4.4 | 写入链路：客户开通流程「资源配置」节点完成时写 link（幂等，按 `customer_profile_id + resource_id` 去重） |
| G4.5 | 联动：供应资源下架/归档时，把关联 link 置 **`SUPPLY_OFFLINE_PENDING`（待处理）**，**不自动停用**；由运营在客户详情或工作台**人工确认**后才转 `SUPPLY_OFFLINE` + 归档。确认前客户仍可用（但列表与详情须显著提示"来源已下架待处理"）。**恢复上架分两种**：① 仍处于「待处理」且**未确认** → 自动回原状态（`state_before_offline`，因为客户从未真正断服，不该罚人工重配）；② 已人工确认归档 → **不自动恢复**，需人工重新配置 |
| G4.6 | 回填（可选）：从 `customer_quote_item.resource_id` 推导历史生效绑定，**只回填能唯一确定的**，其余留空 |
| G4.7 | 审计：所有状态变更写 `operation_log`（before/after/reason） |

**验收**：客户详情能按模型展开到来源；禁用后该客户该模型不再可用；供应资源下架后关联绑定变 `SUPPLY_OFFLINE`；两个唯一索引能挡住重复绑定（写并发测试）。

## 7. 分支与提交约定

- 分支：`feat/prototype-gap-fill`
- 每个 G 独立提交，提交信息格式：`feat(供应商报价): ...` / `feat(客户绑定): ...`
- 数据库迁移单独一个提交，便于回滚
- PR 前跑：后端 `go build ./... && go test ./...`，前端 `npm run build`（或仓库既有校验命令）
- `文档资料/` 已加入 `.gitignore`，不参与提交
- **后端环境（2026-11-03 实测）**：`go.mod` 要求 `go >= 1.26.0`，若本机是 1.25 且 `GOTOOLCHAIN=local`，直接 `go build` 会报版本错。用 `GOTOOLCHAIN=auto go build ./... && GOTOOLCHAIN=auto go test ./...`（会自动拉匹配的工具链）。这只是环境变量，**不要改 Makefile**，免得影响其他人。
