## 二、P0（阻塞）：所有行读回来都没有「准入配置组」

### 现象
`GET /api/supplier/submissions/38` 返回：
```json
{"id":"49","interface_model_id":"qa-claude-east","standard_model_id":"15",
 "test_base_url":"https://a.qa.local/v1",          ← 快照是按组算的（对）
 "test_config_group_id":"",                         ← 实际库里是 15
 "test_config_group_name":"",
 "test_config_group_enabled":false}
```

### 真库对照（只读）
```
submission_row 49 → test_config_group_id = 15 , test_base_url = https://a.qa.local/v1
submission_row 50 → test_config_group_id = 16 , test_base_url = https://b.qa.local/v1
```

### 根因（代码定位）
`internal/api/supplier_submission.go:1218` 是全仓**唯一**构造 `submissionRowDTO` 的地方，字面量里**没有给** `TestConfigGroupID / TestConfigGroupName / TestConfigGroupEnabled` 赋值：
```go
item := submissionRowDTO{
    ID: ..., InterfaceModelID: ..., StandardModelID: ..., StandardModelName: ...,
    OfficialID: ..., Coefficient: ..., TestBaseURL: row.TestBaseURL,
    ParticipateTest: row.ParticipateTest,
}
// ← 三个组字段始终是零值
```
仓储层是好的：`Rows()` 已 SELECT `r.test_config_group_id, g.name, g.enabled` 并 Scan 进 `SubmissionRowRecord`；只有 API 层漏了搬。

### 用户可见后果（这是为什么定 P0，不是"少个字段"）
1. **「准入配置组」下拉永远空白**：保存/刷新后用户选过的组"消失"。
2. **提交按钮永远禁用**：`rowsWithoutGroup = rows.filter(r => !r.test_config_group_id)` 恒为全部行 → `gateError` 第一条就命中「还有 N 个模型没有选择准入配置组。」→ **多配置组的提交链路在 UI 上完全不可达**。
3. 每行还会误报「该组尚未配置 Key」（`!groupByID("")?.has_api_key` 恒真）。
4. 这就是主理人最担心的「前端拦、后端放」，而且是**必然发生**、不是边界场景。

### 修复建议
DTO 构造处补三行（值都已在 `row` 上）：
```go
TestConfigGroupID:      strconv.FormatInt(derefInt64(row.TestConfigGroupID), 10), // 未挂组给 ""
TestConfigGroupName:    row.TestConfigGroupName,
TestConfigGroupEnabled: row.TestConfigGroupEnabled,
```
并补一条单测钉住「读回的行必须带组 id / 组名」，否则这类"结构体少搬字段"的漏永远不会被发现（编译期不报错）。

## 三、逐项证据

### ① 组序号两端一致 —— 后端通过
卡片刻序：`原单组配置(2, sort0)` → 第 1 张；`QA华东通道(15, sort1)` → 第 2 张；`QA华南通道(16, sort2)` → 第 3 张。
草稿 38：row49→组15、row50→组16，均无测试结果。**直接打接口**：
```
POST /api/supplier/submissions/38/submit  {"expected_revision":"1",...}
→ 409 {"code":10005,"message":"第 2 组「QA华东通道」还没有连通成功的模型，请先在该组发起连通性测试"}
```
- 序号 = **2**（与卡片位置一致）✅
- 未提「第 1 组」「第 3 组」→ 未使用的组不参与 ✅（②的负向证据）
- 修复前此处会是「第 1 组」（按用到的组重新计数），本轮修复生效 ✅

**前端侧**：`gateError` 用 `groups.value.findIndex(...)+1`，`groups` 由 `sort_order,id` 排序；后端 `groupGateOrder()` 同样按 `sort_order,id` → **算法同序，代码级一致**。
⚠️ **但没做浏览器验证**：因为 P0 让 `gateError` 在第一条（未挂组）就短路，序号分支在 UI 上根本执行不到。**P0 修完需复验这一条。**

### ② 组集合取法 —— 负向通过，正向未验
- 负向 ✅：上面的 409 只点了第 2 组；空组（第 1、第 3）没被提，说明两端都只用"本次申报挂载过的组"。
- 正向 ❌ **无法验证**：要观测"放行"，需要至少一组里有**连通成功**的行；本轮禁跑测试，无法产生。存量带结果的行（如 row 33）一旦换组立即失效（见 ④），也构造不出"用到组已通过 + 存在空组"的放行场景。
- 代码级：后端只遍历 `coverage`（来自行）的组；前端只遍历 `usedGroups`（来自行）→ 同源。**但这只是读码结论，不等于跑通。**

⚠️ **验证深度限定**：只验到**快照/指纹层**。**没有**真发单验证「A 组的 Key 只打 A 组的接口」——本轮禁跑测试，发单那一层谁也验不了。所以"隔离"的结论只能说到"每行取的是自己组的凭据"，不能说到"发出去确实打对了地址"。

## 四、次要发现（非阻塞）

1. **`PATCH /test-config-groups/:id` 必须带 `name`**，只传 `base_url` 会 400「请填写配置组名称」。但前端 api 的类型注释写的是「局部更新：只传要改的字段」，两者不一致（前端实现总是带 name，所以无用户影响）。建议二选一：后端支持真·局部更新，或改注释。
2. **存量草稿不受影响**：迁移已把存量行回填到组 2「原单组配置」（`base_url=demo`），与行快照一致 → **不会产生 stale**（④ 里换回组 2 后 stale 自动清除即为证据）。所以"改造后存量草稿需要重测"这个担心不成立。
3. **组停用仍参与校验**：按主理人口径（在途申报不卡死），未做反向验证（需测试结果才能走到那一步）。
