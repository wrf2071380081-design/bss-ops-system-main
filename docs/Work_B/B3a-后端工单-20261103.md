## 1. 新增 `GET /internal/customers/:id/operation-logs`（M8:V）

### 为什么
客户详情「操作记录」Tab 目前**没有可用数据源**：
- 内部现成的 `/api/internal/audit-logs`（M12:V）读的是 `audit_log` 表（`internal/repo/workbench_alert.go:274` `func (auditRow) TableName() string { return "audit_log" }`），而**该表在本库不存在**（`information_schema` 只有 `operation_log`）
- 供应商门户的 `/api/supplier/account/operation-logs` 只服务供应商自身（`internal/api/supplier_account.go:369`）
- 我们写客户操作时用的是 `operation_log`（B1 的 `entity_type='customer_profile'`、B2 的 `entity_type='onboarding_flow'`）

### 怎么做
- 读 `operation_log`，条件：`(entity_type='customer_profile' AND entity_id=:id)` **OR** `(entity_type='onboarding_flow' AND entity_id IN (该客户的 flow ids))`
- 返回：`{list, total, page, size}`，每行 `id, action, entity_type, entity_id, operator_name_snapshot, reason, before, after, request_id, created_at`
  - 注意列名是 **`operator_name_snapshot`**（`operation_log` 没有 `operator_name`），别去找不存在的列
  - `before` / `after` 是 **jsonb**，**以 JSON 字符串原样返回**，前端自行决定展示（不要在服务端结构化成对象再序列化）
- 动作文案映射：参考 `supplier_account.go:118-120` 的 `actionLabels`（`CREATE` / `START` / `COMPLETE_CONTRACT` / `COMPLETE_CONFIG` 等），**前端不自己翻译**
- 权限 `perm.M8View`；**404/403 不要另写一套**：直接复用 B1 的 `customer.RegistryService.Profile`
  （已区分 `ErrCustomerProfileNotFound`→404 / `ErrCustomerOutOfScope`→403），避免数据域口径漂移

### 验收
- 建客户 + 发起开通 + 完成两个节点后，该接口应返回 **4 条**（CREATE / START / COMPLETE_CONTRACT / COMPLETE_CONFIG），时间倒序
- 不存在的客户 → 404；别的销售名下的客户（SELF 域）→ 403
- 响应里不出现 `operation_log` 表名、SQL 片段

## 2. 修工作台客户待办 deeplink（跳错页面）

### 现状
`internal/domain/workbench/inbox.go:219-221`（`inboxDeeplink` 的 `case "ONBOARDING_NODE"`）：
```go
case "ONBOARDING_NODE":
    return "/internal/suppliers?keyword=" + url.QueryEscape(item.BizObject)
```
→ **客户的开通待办点进去，会跳到供应商列表按客户名搜索**。

根因：`v_work_item` 对 `ONBOARDING_NODE` 只给了 `biz_id = onboarding_flow.id`，没给 `kind` / `owner_id`，拼不出客户详情链接。

### 怎么做（**不要动 UNION，也不要动视图**）
`workbench_inbox.go` 的 `workbenchInboxSource` 是 **6 条分支 / 5 个 `UNION ALL`**，每条都显式列同一套列并以 `NULL::bigint AS plan_id` 收尾。加列必须同时改 6 条分支，且会牵动供应商那 5 条——**放弃这个方案**。

改为**服务层当页批量补查**：
1. `workbenchInboxSource` 与 `v_work_item` **一字不动**
2. `InboxService.Inbox()` 取到当页 list 后，挑出 `biz_type='ONBOARDING_NODE'` 的 `biz_id`（= flow id），**一次批量查**：
   ```sql
   SELECT id, kind, owner_id FROM onboarding_flow WHERE id = ANY($1)
   ```
3. 结果塞进 `InboxItem` 新增字段（`FlowKind` / `FlowOwnerID`，标 `json:"-"` 不外泄 API 形状），`inboxDeeplink` 按 `kind` 分派：
   - `CUSTOMER` → `/internal/customers/{owner_id}?tab=onboarding`
   - `SUPPLIER` → **保持现有行为，一字不改**
4. 取不到 kind（防御）→ 回落到现有逻辑

### 上线联动（已定：方案 a）
客户详情前端路由 `/internal/customers/:id` **要 B3b 才存在**。改完 deeplink 后，客户待办会从"跳错页"变成"跳 404"。因此：
- **B3a 与 B3b 同批上线**，不单独发布 B3a
- B3a 的验收**不要求点击可达**，只断言 deeplink 字符串正确
- B3b 交付时补一条端到端：点客户待办 → 落到客户详情「档案与办理」Tab

### 验收
- 客户节点待办 → deeplink 为 `/internal/customers/{customer_profile_id}?tab=onboarding`
- 供应商节点待办 → deeplink **与改动前逐字一致**（回归断言，必须做）
- 每页只增加 **1 次**查询（用查询计数断言，防止实现成"每行查一次"）
- 断言方式：直接对 inbox 结果比对 deeplink 字符串，不用起前端

## 3. 客户列表补「已开通模型数」

### 落点（**注意别加错接口**）
不是 B1 的 `GET /internal/customers/:id`（单客户档案），而是：
- `internal/api/customer_workspace.go:308` `GET /internal/customer-workspace/customers`（M8:V）
- 行结构 `CustomerWorkspaceRow`（同文件 **`:37`** 起）

### SQL
```sql
(SELECT count(DISTINCT l.standard_model_id)
   FROM customer_resource_link l
  WHERE l.customer_profile_id = cp.id
    AND l.archived = FALSE
    AND l.state = 'ACTIVE') AS opened_model_count
```

### 口径（已定，别改）
- **只算 `ACTIVE`**：`DISABLED` / `DISABLE_PENDING` / `RESTORE_PENDING` / `SUPPLY_OFFLINE_PENDING` 都不计入
- 依据：原型最终层 `proto-app.js:1748-1758`
  `new Set(db.links.filter(l => l.customer===id && !l.archived && l.state==='已开通').map(l=>l.model)).size`
- 业务含义：「已开通」= 现在能用，不是"曾经有过关系"
- SQL 旁必须写注释：`与原型一致；禁用/待处理/停供不计入`

### 验收
- 同一客户同一模型同时有 `ACTIVE` + 未归档 `DISABLED` 两条绑定 → 该客户 `opened_model_count` 必须是 **1**（不是 2）
- 只有 `DISABLED` 的客户 → **0**
- 无绑定的客户 → **0**（不能是 null）
- 客户列表接口原有字段全部不变（回归）

## 4. 供应商列表「合同状态」永不命中（**存量缺陷**）

### 现状
`internal/api/supply_chain.go:332`：
```sql
WHEN EXISTS (... n.node_key='CONTRACT' AND n.enabled AND n.status='DONE') THEN '已归档'
```
但**所有活路径写的都是 `'COMPLETED'`**（`native_handling_approval.go:273`、`supply_native_contract.go:71`）→ 这个分支永不命中，供应商合同授信节点已完成时列表仍显示「未登记」。

来源：`supply_chain.go:747`（`SimulateAndAdmit`）写 `status='DONE'`，而 `/simulate` 路由已下线（`router.go:577`）——这是历史数据的出处，也是那个 `DONE` 词的唯一写入者。

### 怎么做
一行：`n.status='DONE'` → `n.status IN ('DONE','COMPLETED')`，与视图（000051）同口径。**不动历史数据**。

### 判据（写进 SQL 注释）
**「已归档」= 至少存在一条 `enabled` 且已完成的 CONTRACT 节点**，不是"当前流程已完成"。

已核实：`contract.status` 只有 `PROCESSING` / `ARCHIVED`（`f12_read.go:123` 强校验，无 VOID/EXPIRED），
所以不存在"合同作废但节点完成 → 误判已归档"的情形；且 `IN_PROGRESS/WAITING_PREDECESSOR` 会优先命中「办理中」分支，不会被老流程盖住。

**已知边界（接受现状）**：同一供应商有多条历史 flow 时，若最新一单 CONTRACT 被 CANCELED（`enabled=false`），
老单的 COMPLETED 仍会让它显示「已归档」。这是正确的（老单确实办过合同）。若要"以最新流程为准"，
需加 `ORDER BY flow.id DESC LIMIT 1` 子查询，**不属一行修复，单独排期**。

### 验收
- 该供应商合同授信节点为 `COMPLETED` 且 `contract` 表无 ARCHIVED 记录时，列表显示 **「已归档」**（改前是「未登记」）
- **反向断言（措辞已修正）**：节点未完成时**不得显示「已归档」**——判为「办理中」或「未登记」都算通过
  （不要为了对齐字面去改分支顺序）
- 这是存量修复，commit message 里注明「存量缺陷，非 B2 引入」
