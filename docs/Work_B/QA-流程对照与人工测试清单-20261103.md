## 0. 三句话先对齐

> 🔴 **开始点之前先看这一条：内部页面统一用 `smoke_admin` 登录，口令 `Test@1234`**（`staff_id=3`，`PLATFORM_ADMIN`+`MODEL_OPS`，`data_scope=ALL`）。主理人已用真实 `POST /api/internal/auth/login` 实测该账号返回 200 + token。
> 它是 `PLATFORM_ADMIN` + `MODEL_OPS`，**数据域 `ALL`**，客户域 `M8` 全 + `M9` 全、`can_approve_supplier=true` —— **一个人能走完 A~F 全部流程，并且能看到全部客户**。
> 不要用 `sales_op` 当主账号：它的数据域是 **`SELF`**，**只能看到 `owner_sales_operator_id = 14` 的客户**，灌完数据进去可能只显示一两个甚至空的，很容易被误判成"数据没灌进去"。

1. **原型是前端 mock + localStorage，本系统是真实后端**。原型里"按钮点了没反应"是权限静默 return；本系统里没权限的按钮**直接不渲染**，所以"看不到按钮"通常是权限，不是坏了。
2. **一级导航完全一致**：工作台 / 标准模型库 / 模型广场 / 供应商管理 / 客户管理，5 项同名同序。
3. 本轮验收只覆盖：**客户开通全链 + 客户详情 4 Tab + 客户绑定与上下架联动 + 供应商侧两处补口**。原型里其余没做的，下面的表里都单独标了「本轮范围外」，**不是缺陷**。

> 🔴 **流程 B 的红线（本轮验证结论会写进报告，用户操作务必遵守）**
> `提交申报` 的前提是「测试已完成」，而测试只能通过**真实调用测试平台**完成。仓库里**没有**"人工补传测试报告"的接口（已 grep 确认）。
> 结论：**流程 B 在本环境只能走到「保存草稿」，无法安全走完"提交申报"**。要验证后续流程，只能由工程师把 `resource` 直接置为 `ADMITTED` 造种子数据 —— 那样的话 **B/C 两段流水（申报→审批→接入）本轮没有任何运行时证据**，报告里会明确标"未验证"。

### 权限速查（按**真实库里的角色**读出来的，迁移 `000007` + `000031`）

| 操作 | 需要权限 | 谁有 |
|---|---|---|
| **全部操作（主测账号）** | 全量权限 + **数据域 `ALL`** | **`smoke_admin`（`PLATFORM_ADMIN`+`MODEL_OPS`）** —— 客户域 M8 全 + M9 全、可审批供应商申报、能看全部客户 |
| 客户列表 / 客户详情 / 接入模型 / 开通进度 / 操作记录 | `M8:V` | 几乎所有内部角色都有（MODEL_OPS / PRICING_OP / OPS_ADMIN / SALES / FINANCE / RETRO_OP / AUDIT_READONLY） |
| 新建客户 / 发起开通 / 完成节点 / 移交 | `M8:E` | **`smoke_admin`（全量）、`sales_op`（SALES）、`retro_op`（RETRO_OP 的 M8 是 E/P/A）** |
| 客户详情「该客户报价」Tab | **`M9:V`** | **所有内部角色都有** |
| 「新建报价」按钮 | `M9:E` | `smoke_admin`、`sales_op`（SALES 的 M9 全） |

> ⚠️ **三个必须知道的现实（会影响你怎么点）**
> 1. **主账号用 `smoke_admin`**：全量权限 + `ALL` 数据域，能看全部客户、能审批，一个人走完 A~F。
> 2. **`sales_op` 不要当主账号**：它权限够（M8 全 + M9 全），但**数据域是 `SELF`**，只返回 `owner_sales_operator_id = 14` 的客户。灌完数据点进去只看到一两个客户时，**先怀疑数据域，不要怀疑"数据没灌进去"**。它只适合用来验 SELF 数据域、以及和 ALL 域做对比。
> 3. **真实库里没有任何角色"有 M8:V 但没有 M9:V"**（我逐个角色核对过 `000007`+`000031` 的授权语句）。所以「纯 M8 账号看不到该客户报价 Tab」这一条，**在真实登录环境下验不了**，只能用前端开发身份验（见用例 12a）。

> 🔧 **验权限的探针法（比读代码可靠，以后一直用）**
> 拿一个**必然通不过字段校验**的 body 去打目标写接口：
> - 返回 **400 字段校验错误** → 权限已通过，是参数问题
> - 返回 **403** → 没这个权限
>
> 例：`POST /customers/999999/transfer` 传非法 body → 400 表示 `M8:E` 已过；`POST /customer-quotes` 空 body → 400 表示 `M9:E` 已过。
> 这样能区分"接口没挂 `RequirePerm`（谁都能进，靠字段校验挡）"和"挂了但当前账号没有"。

    ② 有 `ACTIVE` 绑定但**没有任何报价**的新客户 → 应为「服务中」（新增口径）；

  2. 客户详情「接入模型」：**模型服务状态 =「来源待处理」**（不是「服务中」、也不是「已禁用」）；风险异常出现「来源已下架待处理」

  4. 原始 JSON：该行 `service_state == "来源待处理"`，`risk_flags` 含「来源已下架待处理」，且该行 `links[].available_actions == ["OFFLINE_CONFIRM"]`（**不应出现系统动作** `SUPPLY_OFFLINE` / `SUPPLY_RESTORED`）
  5. **点「确认停用」之后**：该条绑定变 `SUPPLY_OFFLINE` + `archived=true`；但**该模型行会整行从「接入模型」里消失**（投影以"未归档绑定"为驱动），Tab 变成空表并显示「该客户还没有接入任何模型」—— **这是当前实现的行为，不是你把模型删了**（见「已知边界」）
- **后续步骤（A2 补完后必须能走通，否则这条状态就是个死胡同）**：
  5. 客户详情「接入模型」→ 展开该模型行 → 应能看到这条绑定，且按钮里有**「确认停用」**
  6. 点「确认停用」并填原因 → 绑定被归档；**该模型行整行消失**（不是变「无可用来源」，见「已知边界」）。重复提交/用旧版本号重放 → HTTP 409，文案是**「客户绑定已归档，不能再变更」**（不是"已被其他人修改"，两种都是人话、都不含 SQL 原文）
  7. 若 A2 未交付：展开区不存在 / 没有任何按钮 → **这是 A2 那条缺陷的表现**，记问题，不要记成"设计如此"
- **失败最可能原因**：
  - 1 分钟后仍是「服务中」→ 后台 `event-deliver` 任务没跑（或 `event_outbox` 里事件仍 `PENDING`）；看 `select status,event_type from event_outbox order by id desc limit 5`
  - 直接变「已禁用」→ 不符合设计（下架**不自动停用**，只标待处理）
  - 已开通模型数没变 → 口径错（应为 `archived=false AND state='ACTIVE'` 去重）
  - 第 5 步没有「确认停用」→ A2 未交付（前端仍无动作入口）

## 附录 · 4 个待定项的结论（已拍板，2026-11-03）

### A1 客户「服务状态」不跟开通流程走 → **已定：改**

**现象**：`internal/api/customer_workspace.go:178-188` 里客户列表的 `service_status` 是**按报价条数**推的（有 `EFFECTIVE` 报价 → 服务中；有 `DRAFT/PENDING/APPROVED` → 接入中；否则 → 潜在客户）。
后果：**开通流程全做完、绑定已生效，列表仍显示「潜在客户」** —— 对用户来说"流程走完了状态没变"就是功能坏了。

**定论**：改。**在现有逻辑上加 OR，不推翻原口径**：
- 有 `EFFECTIVE` 报价 → 服务中（保留）
- **或** 存在 `archived=false AND state='ACTIVE'` 的客户来源绑定 → 服务中（**新增**）
- 有 `DRAFT/PENDING/APPROVED` 报价 → 接入中（保留）

**明确不做**：不要改成"只看绑定"。否则**没有绑定的老客户会全部掉回「潜在客户」，那是回归**。
**验收口径**：用例 7 的「口径核对」里列了 3 类客户必须同时核（老客户保口径 / 新客户新口径 / 空客户不误伤）。

### A2 客户侧「禁用 / 恢复 / 确认停用」前端零入口 → **已定：是漏了，必须补**

**不是"本轮不做"。** G3-0 刚做完下架联动，把绑定推进 `SUPPLY_OFFLINE_PENDING`，而这个状态**唯一的出口就是 `OFFLINE_CONFIRM`**。前端没有入口 = **绑定永久卡在「来源待处理」，没有任何人能在界面上把它处理掉**。自己造一个"进得去出不来"的状态，比"没有这个功能"更糟。

**定论**：A2 与 A4 的「展开资源」合并为同一件活 ——
**客户详情「接入模型」Tab 每行可展开，展开后显示该模型下的绑定明细 + 按状态机显示可用动作**
（`DISABLE_REQUEST` / `DISABLE_CONFIRM` / `RESTORE_REQUEST` / `RESTORE_CONFIRM` / `OFFLINE_CONFIRM`，对应 `POST /api/internal/resource-links/:id/actions`）。
后端接口与状态机已就绪，纯前端接入口；动作必须带 `expected_revision`（乐观锁，冲突返回 409）。

**验收口径**：用例 10 第 5~7 步（下架 → 展开 → 确认停用 → 归档生效）。

### A3 完成节点不校验"是不是该节点的指定办理人" → **已定：不改（已知边界）**

`customer.OnboardingService.CompleteNode` 只校验 `M8:E` 和节点状态，不校验 `operator == node.assignee_id`。

**不改的理由**：客户开通是**内部运营动作**，`M8:E` 本身就是粗粒度授权，不需要再细分到人；供应商侧之所以要校验，是因为**跨主体**（不同供应商的人不能互相办），客户侧不存在这个问题。

**写进「已知边界」的一句话**：
> **指派只决定待办落到谁的收件箱，不构成办理权限。** 任何持有 `M8:E` 的账号都可以办理任何客户的开通节点。

对应地，用例 8 的前置条件已改为"用任意有 `M8:E` 的账号都能办；想让待办出现在自己名下才需要把自己设为办理人"。

### A4 「接入模型」Tab 缺项 → **已定：拆两半**

| 缺项 | 结论 | 说明 |
|---|---|---|
| **「每行可展开 → 绑定明细 + 行内动作」** | **本轮补** | 与 A2 是同一件活，A2 的承载载体；不补则 A2 无法交付 |
| **「当前报价系数」列** | **本轮范围外，需后端加字段** | `resource-links` 接口返回里没有系数字段，补这一列要动后端返回结构，属新增需求。**不是纯前端活**，本轮不做 |

## 已知边界（刻意接受，不是缺陷 —— 看到这些现象不用报 bug）

| 边界 | 说明 |
|---|---|
| **「确认停用」后模型行会整行消失** | 绑定归档后不再有"未归档绑定"，而「接入模型」Tab 的投影正是以未归档绑定为驱动的（`WITH bound … GROUP BY standard_model_id`），所以该模型行会**整行消失**，Tab 显示空表文案「该客户还没有接入任何模型」——而不是停留在一行「无可用来源」。用户容易理解成"模型被删了"。文案/交互是否调整待产品定，行为本身符合当前设计。 |
| **「合作阶段」也受生效绑定影响** | 客户列表的「合作阶段」与「服务状态」由同一个判断分支赋值：存在 `archived=false AND state='ACTIVE'` 的客户来源绑定 → **合作阶段也为「已有」**（不只是服务状态变「服务中」）。所以"零报价但有生效绑定"的客户（本轮灌数据产生的）会同时显示「已有 + 服务中」。**按「合作阶段=已有」筛选时，会把这些客户一并筛出来**，这是口径的连带结果，不是 bug。
| **指派 ≠ 办理权限** | 客户开通节点的「办理人」只决定**待办落到谁的收件箱**，不构成办理权限。任何持有 `M8:E` 的账号都可以办理任何客户的任何开通节点（客户开通是内部运营动作，不存在供应商侧那种跨主体问题）。 |
| 客户侧合同授信不走 F12 就绪 | 唯一实现是 `NativeSupplierF12`（只覆盖供应商）。客户侧改为"办理人确认 + 必填说明"，节点 note 里会写「F12 就绪能力待客户版 provider 就绪后启用」。 |
| `onboarding_flow` 无任何外键 | `owner_id` 是多态字段（供应商 / 客户档案共用），一个外键无法兼顾。做"删除客户"时必须手工清三张表，否则留孤儿。 |
| 客户重名是**查询判重**、非唯一索引 | 并发下理论上可能建出两条同名（人工新建是低频操作，代价已接受）。单线程人工测试不需要考虑。 |
| 合同状态优先级 `办理中 > 已归档 > 未登记` | 有流程在办时显示「办理中」而不是「已归档」——「已归档」是结案信号，会让人停止推进。 |
| 客户主体仅支持 `COMPANY` | 个人主体后端直接 400（缺 `mobile`/`real_name`，半成品入口比拒绝更糟）。 |
| 已开通模型数只算 `ACTIVE` | 禁用 / 禁用待确认 / 恢复待确认 / 来源待处理 / 停供**都不计入**。这些状态在客户详情「接入模型」里仍可见，只是不进这个计数。 |
| 下架不自动停用客户绑定 | 资源下架只把绑定标成 `SUPPLY_OFFLINE_PENDING`（来源待处理），**不自动停用**——自动停会误伤正在用该来源的客户。人工确认后才归档。 |
