## 一、这个 PR 解决什么

产品给了新版原型（`TokenOps-Latest.html` 最终渲染层），对比后发现现有系统**不是缺架构，是缺最后一段**：
一级导航 5 项完全一致，差异集中在「详情页结构」和「3 个真缺的块」。本 PR 只做后者，**不做文案/口径调整**。

三个真缺的块：
1. **客户—模型—供应来源的绑定关系** —— 现有系统完全没有这层对象，客户只靠报价单间接关联
2. **供应商管理的「供应商报价」Tab** —— 原来藏在隐藏路由里，且那个页面是 SKU 价格报价，不是接入申报审批
3. **批量上架/下架** —— 只有单条接口（**本 PR 只做了联动前置，批量功能未做**）

## 二、按块说明（review 顺序建议按此）

### 1. 客户绑定对象（后端，唯一动数据库的部分）
- `migrations/000049_customer_resource_link.*` —— 新表，直挂 `customer_profile`，**两个部分唯一索引**：
  - 同客户同资源只能有一条未归档
  - 同客户同模型只能有一条 `ACTIVE`（换来源必须先归档旧的）
- `internal/domain/customer/link.go` —— 6 状态机：`ACTIVE / DISABLE_PENDING / DISABLED / RESTORE_PENDING / SUPPLY_OFFLINE_PENDING / SUPPLY_OFFLINE`
- `internal/infra/supplypg/customer_resource_link_store.go` —— 仓储 + 乐观锁 + **审计与状态同事务**（`ApplyTransition` 里 `UPDATE ... RETURNING` + 审计 INSERT 一个 tx）
- `internal/api/customer_resource_link.go` —— 投影 / 建绑定 / 动作

> **注意**：`SUPPLY_OFFLINE_PENDING` 是刻意设计——资源下架**不自动停用**客户绑定，只标记待处理，人工确认后才停。因为自动停会误伤正在用该来源的客户。

### 2. 客户创建与开通流程（后端）
- `POST /internal/customers` —— `legal_subject` + `customer_profile` **同事务**，任一步失败整体回滚（不留孤儿主体）
- `onboarding_flow kind='CUSTOMER'`（`000050`）—— 节点 `CONTRACT`（首单）+ `CONFIG`；CONFIG 完成时按模型**逐行写绑定，整批原子**
- `000050` 同时修 `v_work_item` **两个存量 bug**（见第三节）
- `000051` —— 视图兼容历史 `status='DONE'` 节点

### 3. 资源上下架 → 客户绑定联动（后端）
- 挂现有 `event-deliver` job，监听 `RESOURCE_OFFLINED` / `RESOURCE_ONLINED`
- **一条资源 N 个客户**：逐条 CAS + 独立事务，单条 409 只跳过该条
- 修 `event_deliver.go` 的"未配 webhook 就完全 return"——原来会导致事件永远 PENDING、**DEAD 告警永不触发**

### 4. 供应商侧（前端为主）
- 供应商管理加二级 Tab（供应商列表 / **供应商报价**），报价 Tab 内两段：接入申报 + 价格报价
- 供应商详情 4 Tab 重排 + 接入模型表补 6 列（连通耗时 / RPS / TPS / 缓存命中率 / 上架时间 / 测试与报告）
- 删孤儿组件 `WorkbenchApprovals.vue` 与已下线接口调用

### 5. 客户侧前端
- `/internal/customers/:id` 整页 4 Tab（接入模型 / 档案与办理 / 该客户报价 / 操作记录）
- 建客户**两步向导**（建客户 → 发起开通），含失败恢复：Step1 成功 Step2 失败时保留 `customerId`，**不会重复建客户**
- 客户列表加「已开通模型数」（只算 `ACTIVE`，按模型去重）

## 四、验收证据（都是实测，不是"读代码觉得对"）

| 项 | 验证方式 |
|---|---|
| 两个部分唯一索引 | 真实 PG 构造：两条 ACTIVE 被拒；归档后名额释放；`DISABLED`+`ACTIVE` 共存允许 |
| 下架"客户仍可用" | 库级断言 `archived=false`（不是靠文案） |
| 已归档不可被"上架事件"复活 | 三层：服务层 + 仓储 + SQL `WHERE archived=FALSE`；事后查库数据未变 |
| 视图两个 bug | 同一事务内换回 000035 旧定义、对同一行查对照（旧：`TODO`/空名/空区；新：`DONE`/真名/CN），再 ROLLBACK，用 `pg_get_viewdef` 哈希确认回滚生效 |
| CONFIG 批量写绑定原子性 | 两种唯一索引冲突各测：本来能成功的模型**一行没落库**，flow/node/审计均未前进 |
| 未配 webhook 从死到活 | **修前/修后对照**：父提交 `PENDING retry=0`（永远不动）→ 本分支 `DONE` + 联动生效 |
| 审计与状态同事务 | PG 触发器强制 `operation_log` 插入失败 → 动作报错，而绑定**仍 ACTIVE、revision 未变** |
| deeplink 测试有效性 | 变异验证：把客户分支改错 → 测试立即红（证明不是空转断言） |

## 六、已知边界（刻意接受，不是遗漏）

1. **客户侧合同授信不走 F12 就绪**：`ResolveF12BusinessContext` 唯一实现是 `NativeSupplierF12`，非 SUPPLIER 直接 `ErrDependencyUnavailable`。改为**办理人确认 + 必填说明**，节点 note 写明「待客户版 provider 就绪后启用」
2. **`onboarding_flow` 无任何外键**：`owner_id` 多态（supplier / customer_profile），一个外键无法兼顾。做"删除客户"**必须手工清三张表**
3. **客户重名查询判重**、非唯一索引：并发下可能两条同名（已测不产生脏数据），避免动既有数据与索引
4. **合同状态优先级 `办理中 > 已归档 > 未登记`**：有流程在办时显示「办理中」，因为「已归档」是结案信号会让人停止推进
5. **客户仅支持 `COMPANY`**：`INDIVIDUAL` 返回 400（缺 `mobile`/`real_name`，半成品入口比拒绝更糟）
6. **已开通模型数只算 `ACTIVE`**：与原型 `!archived && state==='已开通'` 一致
