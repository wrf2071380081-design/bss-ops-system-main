## 一、事务语义：**逐条独立事务**（已定）

| 依据 | 说明 |
|---|---|
| **锁面（决定性）** | `Create` 内部 `ResourceForPlanCreation` 走 `state.ForUpdate`（`plan_store.go:425-436`），每条锁一行 `resource`。50 条包进外层事务 = **同时持有 50 个行锁**，而执行链路也要锁 resource + plan → 长事务放大锁等待甚至死锁 |
| 业务无跨行不变量 | 每条计划是独立对象（自己的 `BuyerID` 校验 / `HasPendingStatePlan` / 前置状态检查），一条失败回滚另外 49 条 = 让用户重勾一遍，**更差不是更安全** |
| 与既有批量语义一致 | 批量接入已是"部分成功保留 + 逐条回执"；批量建计划破坏性更低，无理由要求更强原子性 |
| 重试自愈 | 同幂等键重试，已成功的那几条会因 `HasPendingStatePlan` 返 409 而非重复建 → **天然防重**（方案乙整体回滚后反而分不清哪些原本成功） |

**因此不照抄批量接入的 `SAVEPOINT` 写法**——那是"同一 tx 内分段回滚"，需要 writer 支持 context tx（即被否掉的方案乙）。甲的实现更简单：不碰 tx，逐条调用。

## 二、接口

`POST /internal/plans/batch`（`requireSupplyInternalStaff` + 幂等）

```
{ kind: "ONLINE"|"OFFLINE", due_at, reason,
  items: [{ resource_id, expected_resource_revision }] }   // 1~50 条，resource_id 去重
```

**逐条**调 `PlanMaintenanceService.Create`，错误映射：

| 错误 | 状态 | 回执 message 要点 |
|---|---|---|
| `ErrForbidden` | 403 | 不是你的资源（采购归属人不符） |
| `ErrNotFound` | 404 | 资源不存在 |
| `ErrRevisionConflict` | 409 | **分两种**：版本已变更 / 已有待执行计划（带 `pending_plan_id` + `pending_plan_status`） |
| `FieldError` | 400 | 资源前置状态不满足（如 `OFFLINE` 计划要求 `state='ADMITTED'`，`ONLINE` 要求 `OFFLINE`） |

响应：`{ results: [{resource_id, status, message, plan_id?}], succeeded, failed }` + `SetIdempotencyResult`。

### 回执文案必须区分 PENDING 与 BLOCKED
`HasPendingStatePlan` 只认 `status='PENDING'`（`plan_store.go:442`），**`BLOCKED` 的计划不拦**。
所以 409 的 message 要带 `pending_plan_status`，否则用户看到"上次那条失败了怎么还能建"会绕不出来。

## 三、前端预检：**本轮不做**，只做逐条回执

硬事实：`GET /internal/plans` 只支持**单个** `resource_id`（`plan_list.go:5-9`），没有多值筛选 → 提交前预检 50 条要发 50 次请求，不可接受。

三条理由不先做预检：
1. **预检必然过期（TOCTOU）**：拉到提交之间有人建了计划，预检就作废。**逐条回执才是唯一权威**，顺序不能反
2. **预检覆盖不全**：被拒原因还包括 403（归属人不符）、400（前置状态不满足），只查 PENDING 的预检挡不住这些
3. **灰按钮最难排查**：用户看不到原因也没法绕过

**做法**：409 的 message 带 `pending_plan_id`，前端标红该行 +「查看该计划」跳转（现有 form `…?region=&tab=plans&plan_id=`）。

**后续可选**（G3-1b）：给 `GET /internal/plans` 加 `resource_ids` 多值筛选（`=` → `= ANY`），做"行内提示"但**不置灰**。

## 四、前端（本轮范围）
- 模型广场详情：新增选择列（当前无 `type="selection"`）+「批量建上下架计划」按钮
- 供应商详情接入模型页：**独立入口**（不共用批量接入的 selection，避免误提交破坏性动作）
- 结果弹窗：逐条成功/失败 + 失败原因 + 「查看该计划」跳转
- 前端按 20~50 条分批提交（后端上限 50，每条一个事务 = 最坏 50 次往返）

## 五、验收
1. 50 条全成功 → 50 条 PENDING 计划，回执 `succeeded=50`
2. 10 条已有待执行计划 → 这 10 条 409 且 `pending_plan_id` 正确，其余 40 条成功
3. 5 条不是当前用户的资源 → 403，其余成功
4. 同幂等键重试 → 已成功的不重复建（409），不产生第二条计划
5. 超 50 条 → 400；`resource_id` 重复 → 去重后处理
6. `BLOCKED` 状态的计划不拦（能建新的），回执 message 能区分
7. 锁面验证：50 条批量执行期间，另一个请求能正常锁同一批资源中的某一行（证明没有长事务持锁）

## 不做
- 立即执行（G3-2）
- 预检置灰（G3-1b 可选）
