# B-1/B-2 前置调研与建议（2026-10-23）

分支：`feature/supplier-submission-api`（基线 `f6d6cf0`）
目标：把供应商门户那 5 个 404 接口做出来（交接文档 B-1/B-2）

---

## 一、结论摘要

**接口本身不难，但有 3 个必须先处理的阻塞，其中 1 个会直接让服务起不来。**

不处理就写代码的话，最可能的结局是：写完发现启动 panic、或者迁移号撞车、或者前端字段对不上又要返工。

数据库现状：`submission` / `submission_row` 两张表**存在但本机是空的**（0 行）。
同事文档里说的"9 条数据"是在他机器上，没有随代码过来——所以本机没有可参考的真实样本。

---

## 二、三个阻塞项

### 🔴 B1-0a 路由会重复注册，服务启动直接 panic

**证据**
- `internal/api/router.go` 供应商门户块里，同事加了：
  `protected.POST("/submissions", middleware.Idempotency(...), sch.CreateSubmission)`
- 交接文档 B-1 要求正式实现也挂在 `POST /api/supplier/submissions`
- gin 对同一路径重复注册会 **panic**（不是 404、不是后者覆盖，是启动就崩）

**所以只要我在 `registerSubmissionRoutes` 里注册同路径，服务就起不来。**

**三个选项**

| 方案 | 做法 | 代价 |
|---|---|---|
| A（推荐） | 删掉 `supply_chain.go` 里的简化版 `CreateSubmission` 及其路由，正式实现接管 | 演示链路里"供应商提交申报"按钮要先能用新接口，得同时做完创建 |
| B | 简化版保留，正式实现挂别的路径（如 `/submissions/full`） | 与前端契约不符，等于没做 |
| C | 用特性开关二选一 | 多一个配置、多一条分支，接线期最容易忘 |

交接文档第 99 行原话：「正式实现上线时请**替换/删除**它，别两套并存」。选 A，和文档一致。

### 🔴 B1-0b 迁移编号会撞车

- 我的测试分支已经用了 **000038**（`test_report_cache_ratio`）
- 本分支如果也用 000038，两条分支合并时会出现**两个不同内容的 000038**，迁移工具会认为版本相同而跳过其中一个 → 静默漏表

**建议：本分支用 000039**，并在文件头注明"000038 已被测试平台分支预留"。
两条分支合并后顺序为 37 → 38（测试）→ 39（申报），互不依赖，可正常应用。

### 🔴 B1-0c 表结构缺 4 样东西，前端字段对不上

前端 `SupplierSubmissionDTO` 要求的字段，和现表的差距：

| 前端要的 | 现状 | 处理 |
|---|---|---|
| `revision`（乐观锁） | **没有这列** | 迁移新增 `revision bigint NOT NULL DEFAULT 1` |
| `updated_at` | **没有这列** | 迁移新增（`submission` 只有 `created_at`） |
| `submitted_at` 可空 | 现为 `NOT NULL` | 草稿没有提交时间，必须 `DROP NOT NULL` |
| `official_id` / `standard_model_name` | 表里没有 | join `standard_model` 取，不存冗余 |
| `permissions{can_edit,can_submit,can_withdraw}` | 无 | 按状态在服务层推导 |

## 三、契约映射

### 前端 → 数据库

| 前端字段 | 来源 |
|---|---|
| `interface_model_id` | `submission_row.supplier_model_name`（供应商自己的模型 ID） |
| `standard_model_id` / `standard_model_name` / `official_id` | `standard_model` join |
| `coefficient` | `submission_row.coefficient`（decimal 字符串） |
| `test_base_url` | `submission_row.test_base_url` |
| `test_api_key`（写入） | 加密后进 `submission_row.test_api_key_enc`，**读永不返回** |
| `row_status` | `submission_row.row_status` |
| `connectivity_*` / `stress_*` | 由 `test_job` / `test_report` 推导 |
| `kind` | `submission.kind`：`MODEL_NEW` / `PRICE_CHANGE` |

### 一个必须翻译的枚举

前端测试类别用 **`CONNECTIVITY` / `STRESS`**，而测试平台用 **`baseline` / `stress`**。

这层映射必须放在 API 边界（`CONNECTIVITY → baseline`），**不能透传前端值**——否则平台会 400（`category` 只认那 8 个门类）。这也是两个分支合并时最容易踩的接缝。

## 四、三个需要你拍板的口径

### Q-A 测试凭据放"申报行"还是"主体级"？

- 原型文案：「此 URL／Key 专用于我方自研工具测试，**所有申报模型共用**」（主体级）
- 前端契约：`SupplierSubmissionWriteRow` 里带 `test_base_url` / `test_api_key`（**行级**）
- 之前 Q5 的决策：输入按主体级、快照落资源级

**建议：按前端走行级，主体级作为"预填默认值"。**
理由：表结构已经是行级（`submission_row.test_base_url`），前端也这么发了；改成主体级要动表动接口动页面。做法是：进入申报页时用该供应商上次填过的值预填所有行，供应商可逐行改——**体验上像共用，数据上是快照**，两个诉求都满足。

### Q-B 申报单状态机取值

现表无约束，同事的简化版直接写 `PENDING_APPROVAL`。原型有 7~8 个态。

**建议最小集（够 B-1 用，且不与原型冲突）**：

```
DRAFT ──submit──► PENDING_APPROVAL ──approve──► APPROVED ──► PROCESSING ──► COMPLETED
  ▲                     │
  └──── withdraw ───────┘         └──reject──► REJECTED ──(改后重提)──► PENDING_APPROVAL
```

`permissions` 推导规则：
- `DRAFT` → can_edit / can_submit / can_withdraw 全 true
- `PENDING_APPROVAL` → 只有 can_withdraw
- `REJECTED` → can_edit（另存新版本）
- 其余 → 全 false

**风险**：产品还没给权威状态机（早前记录里就标了这条待确认）。我按上面这套实现，但**它属于"可改口径"**，不是终局。

### Q-C `rows/:rowId/test` 现在怎么处理

它要调测试平台，而测试分支还没进本分支。

**建议：先返回 503 + 明确文案「测试平台未接入」**，不要写成 404（404 会被前端翻译成"数据不存在"，更容易误判）。
合并集成分支时，这里只需替换成调用 `testplatform.Service.Start`——**改一处**。

## 五、建议的实施顺序

不建议一口气写完 9 个接口。按"能被验证"切三段：

**第 1 段 · 只读三接口（不需要迁移，当天能出结果）**
`GET /submissions`、`GET /submissions/:id`、`GET /submissions/model-options`
- 依赖：无迁移、不动状态机（`revision` 先按 `1`、`updated_at` 用 `created_at` 顶上）
- 产出：前端三个 tab 至少不 404；`model-options` 用现成的 `standard_model` 就能查
- 注意：本机库没有申报数据，页面会显示空列表——**这是"没数据"，不是"没接口"**，正好用来验证前端 404 提示是否会被误判

**第 2 段 · 迁移 000039 + 写接口**
`POST /submissions`（多行）、`PUT /submissions/:id`（存草稿，乐观锁）
- 必须先解决路由冲突（B1-0a），否则服务起不来
- 加密：`test_api_key` 用现成的 `SecretSealer`；**密钥未配置时，带 key 的写法返回 503**（不允许明文落库）

**第 3 段 · 提交/撤回 + B-2**
`POST /:id/submit`、`POST /:id/withdraw`（都带 `expected_revision`）、`GET /supplier/models`
`rows/:rowId/test` 先留 503

## 六、风险

1. **没有真实数据可参照**。本机库空，同事的样本没过来。写查询时字段含义只能靠前端 DTO 和表结构推，第一次跑真实数据可能要调。
2. **`supplier` 表本机也是空的**（0 行），所以"登录后按 supplier_id 过滤"这条路径本地验不了——除非先造一个供应商 + 账号。
3. **B-2 的 `price-change` 依赖报价体系**（`quote_sheet`），本机 `supplier=0`、`quote_sheet=14` 条但挂在老供应商上，这块建议最后做。
