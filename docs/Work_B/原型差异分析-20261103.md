## 一、结论先说

1. **骨架已经对齐**：左侧 5 项导航（工作台 / 标准模型库 / 模型广场 / 供应商管理 / 客户管理）**同名同序**，无需重做信息架构。
2. **已实现约六成**：严格逐项一致 **57%（78/136 项）**；把"只是叫法不同"的 17 项算进来，功能等价 **70%**；按页面重要度加权（严格口径）**≈59%**。算法见 §七。
3. 剩下的（严格口径 43%，其中只有 16 项是"整块"）不是"架构问题"，而是**两类完全不同的东西**：
   - **表面差异（改文案、补列、加交互，工作量小）**——占差异项的绝大多数；
   - **真缺功能（缺整块页面 / 缺数据对象）**——只有两块：**供应商报价页**、**客户详情与开通**。
4. **两个真缺的块，后端能力其实都在**（申报多行/审批/流程节点/合同授信/资源准入都已实现），缺的是"页面"和"客户-模型-来源这张关系表"。
5. 结论：**增量对齐 + 局部重构**，不推翻。

---

## 二、一句话看懂"两类差异"的区别

原型和现在这套系统，**骨架是同一个**：

```
        工作台   标准模型库   模型广场   供应商管理   客户管理      ← 名字、顺序、位置都一样
          ✅        ✅          ✅         ⚠️          ⚠️
```

差的是挂在骨架上的"肉"，而且分两种：

| 类型 | 大白话 | 例子 | 工作量 |
|---|---|---|---|
| **表面差异**（命名/字段/交互） | 东西都有，就是**叫法不一样 / 少一列 / 少个按钮** | 合同状态原型叫「暂无」我们叫「未登记」；供应商列表少一列「已开通模型数」；列表不能点表头排序 | 小，改文案和列就行 |
| **真缺功能**（缺整块） | 这块**页面上根本没有**，得从零做 | ①「供应商报价」这个二级页完全没有（原型是供应商管理的第二个 Tab）②客户详情没有 4 个 Tab，也没有"客户开通了哪个模型、来源是谁"这张关系表 | 大，要新页面 + 新表 |

**一句话记住**：**表面差异是"改名和补齐"，真缺功能是"开两块新地"。**

## 四、两个"真缺"的块（为什么不能靠改文案解决）

### 1. 供应商报价页（缺整块，但**后端已经好了**）

- **缺什么**：一个二级页面（供应商管理第二 Tab），列表 + 详情审批。
- **不缺什么**：`/internal/approvals/submissions`、`/internal/approvals/history`、`/internal/flows/submissions/:id/approve|reject`、办理人指派、整单审批、幂等与乐观锁，**后端全都在跑**；前端还有一个写好了但没挂路由的 `WorkbenchApprovals.vue`。
- **为什么现在也算"用户能看见的能力"**：目前只能从工作台待办一条条点进去，没有"待审批一共几条、谁交的、几天前的"列表视角。
- **工作量**：前端 1 个页面 + 1 个详情（复用现有弹窗逻辑），后端 0。

### 2. 客户详情与开通（缺整块，**真正的数据缺口**）

- **缺什么**：① 客户详情整页 + 4 Tab；② **「客户-模型-来源」绑定对象**（原型叫 `links`）；③ 开通批次（资源配置 / 合同与授信两个模块）。
- **为什么必须新表**：客户列表要显示「已开通模型数」、客户详情要显示「这个模型的来源是谁、状态是什么」，这些都不是现有任何表能推出来的——现在客户"服务中"是**按生效报价条数猜的**（`api/customer_workspace.go:162-178`）。没有绑定表，这两列只能造数。
- **好消息**：`onboarding_flow` 表已经允许 `kind='CUSTOMER'`，节点枚举也预留了 `ACCOUNT/CONFIG`（`migrations/000033:272-294`）；合同授信可以复用现有 `F12SubjectPanel`（已支持 `subject-type="CUSTOMER"`）。
- **工作量**：新表 + 建流程/推进/完结 3 个服务 + 详情页 + 列表两列，是本轮唯一需要动数据库的一块。
