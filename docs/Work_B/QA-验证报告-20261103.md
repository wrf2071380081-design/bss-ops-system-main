## 四、三处「预期与实际不符」（**指南必须这么写，否则用户会误判**）

### 4.1 `opened_model_count` 不会因「确认停用」而减少
该字段**只算 `ACTIVE`**。「来源待处理 / 已禁用 / 停供」都不计入。
所以对一个**本来就是待处理**的来源点「确认停用」，这个数字**前后不变**（373 一直是 1，那 1 来自另一条 ACTIVE 绑定 753）。
→ 用户要看的是**模型行消失**，不是看这个数字。

### 4.2 「确认停用」后，该模型行**整行消失**（**已修复，commit `2e475a7`**）
不是变成「无可用来源」。因为「接入模型」投影**以未归档绑定为驱动**（`WITH bound … GROUP BY standard_model_id`），归档后没有任何未归档绑定 → 这一行根本不产生。
表现（修复前）：Tab 变空表，文案「**该客户还没有接入任何模型**」——用户极易理解成"模型被删了"。

**修复方式**（前端表达层，未动 SQL 投影）：动作成功后若动作 ∈ `{"OFFLINE_CONFIRM"}`（与后端 `ArchivedAfter` 一致，`DISABLE_CONFIRM` 不归档故不置位），置会话内标记，空表文案变为「**该模型来源已停用并归档，可到「操作记录」查看本次操作**」。
**验收点**：确认停用后表格应显示这句新文案，而不是「该客户还没有接入任何模型」。

**残留边角（低危，未修）**：该标记只置不清。因为详情页**没有 `watch(customerId)`**，若在 `/customers/373` 直接改 URL 到 `/customers/375`（同一组件实例被复用，`router-view` 的 key 是用户 id），会既显示 373 的旧数据、又沿用"已停用并归档"文案。正常 UI 路径（列表 → 详情）会重新挂载，不受影响。详情→详情不重载本身是**既有问题，不是本轮引入**，建议另立小工单。

### 4.3 409 文案是「客户绑定已归档，不能再变更」
不是"已被其他人修改，请刷新后重试"（那句属于并发改同一条**未归档**绑定的场景）。两句都是人话、都不含 SQL 原文。
