## 1. 结论与规模判断

> **2026-11-03 修订 v2**：初版把「客户开通 / 客户-模型-来源 link」判为旧层遗留并排除，该结论**已被推翻**。经复核 `proto-app.js:3949` 起的最终渲染层，`db.links` 在最终层被引用 109 次且写入点明确（`:265`、`:1123`），客户详情为整页 4 Tab（`:13685`），客户侧开通流程同样折叠为 **2 个模块卡**（`clientModules20 = {ops, business}`，`:1065`）。因此新增 **P5 阶段 + W21–W25**。
> **2026-11-03 修订 v3**：初版与 v2 把「商务记录多办理人 + 线下办理人」判为旧层遗留，**同样被推翻**。最终层写入侧是多选（`:374` `node-handler` 多选、`:376` 多值提交、`:379/:380` 资料表单多选），展示侧多值（`:2047`、`:5333`）。因此新增 **W26**。两次误判的根因相同（见 §10.4 方法论留痕）。

**总规模：中偏大 —— 约 36~41 人日（单人约 7.5~8 周，双人并行约 4~4.5 周），共 26 个工作项（S×9 / M×13 / L×4）。**
**若 Q9 选"本期只做读多办理人"（W26 降为 M）：约 34~39 人日。**

一句话理由：**P1–P4（原 20 项）仍是"末段对齐"，95% 是前端渲染与文案口径，后端只有 3 处小改动；P5 是唯一"从 0 到 1"的部分 —— 客户-模型-来源 link 对象（新表 + 状态机 + 写入联动）、客户详情整页 4 Tab、「已开通模型数」改为从 link 派生，以及 F12 商务记录多办理人（新关联表 + 写入契约 + 附件鉴权改造）。两块都建新表但不推翻任何现有表：`customer_link`（000033）零使用且挂在另一套客户模型上，不复用；`contract`/`credit_line`（000044）只加关联表、不动主键与 CHECK。**

### 2.1 表选型：新建 `customer_resource_link`，不复用 000033 的 `customer_link`

**结论：新建 `customer_resource_link`，直挂 `customer_profile(id)`；`customer_link`（000033:332）保持空表不动，建议后续随 000033 目标模型整体收敛时再清理。**

| 方案 | 可行性 | 结论 |
|---|---|---|
| **A. 复用 `customer_link`**（000033:332） | 表结构本身够用（`customer_id/resource_id/standard_model_id/state/sale_coefficient/quote_snapshot/requirements/activated_at/archived`），且已有 `uk_customer_link_active(customer_id, resource_id) WHERE archived=false` | **不选**。三个硬伤：① `customer_link.customer_id → customer(id)`，而客户管理全程读 `customer_profile(id)`（`customer_workspace.go:120-135`），**两套客户模型无任何映射字段**；② `customer`/`quote`/`customer_link` 三张表在 Go 侧**零引用**（`grep 'public.customer'` = 0），是建了没接线的空壳；③ 复用就得先给 `customer` 造数据并维护 `customer ↔ customer_profile` 双写，**双写即埋一致性债**，且 `customer_link` 现在被 `supplier_merge_preview.go:86` 当计数用，语义会被污染 |
| **B. 新建 `customer_resource_link`**（推荐） | 沿用原型 `db.links` 的字段与状态机 1:1，改挂 `customer_profile` | **选 B**。零回填、零双写、不触碰 000002/000005/000048 任何现有链路；代价是多一张表（可接受，因为语义本来就不同） |

**建议 DDL 要点（`migrations/000049_customer_resource_link.up.sql`）**：

```sql
CREATE TABLE customer_resource_link (
  id                  bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_profile_id bigint NOT NULL REFERENCES customer_profile(id),
  resource_id         bigint NOT NULL REFERENCES resource(id) ON DELETE RESTRICT,
  standard_model_id   bigint NOT NULL REFERENCES standard_model(id),
  flow_id             bigint NULL REFERENCES onboarding_flow(id),   -- 000033 已有此表
  state               varchar(24) NOT NULL DEFAULT 'ACTIVE',
      -- ACTIVE / DISABLED / DISABLE_PENDING / RESTORE_PENDING / SUPPLY_OFFLINE_STOP
  sale_coefficient    numeric(8,4) NULL,
  quote_snapshot      jsonb NULL,      -- 开通时报价快照，历史不重写
  requirements        jsonb NULL,      -- 客户指标要求（rps/准确率…）
  activated_at        timestamptz NULL,
  stopped_at          timestamptz NULL,
  archived            boolean NOT NULL DEFAULT false,
  created_at / updated_at / created_by / request_id ...
);
CREATE UNIQUE INDEX uk_crl_active ON customer_resource_link(customer_profile_id, resource_id) WHERE archived = false;
CREATE INDEX idx_crl_model  ON customer_resource_link(customer_profile_id, standard_model_id) WHERE archived = false;
CREATE INDEX idx_crl_resource ON customer_resource_link(resource_id) WHERE archived = false;  -- 支撑「受影响客户」查询
```

**回填策略：零回填。** 历史"已开通"在系统里**没有数据源**（现有只有客户报价 `customer_quote_item.resource_id`，那是"报过价"不是"已开通"）。若强行用报价反推，会出现"客户列表显示已开通 N 个模型、点进详情却没有任何 link 记录"的自相矛盾。→ 新表从空开始，「已开通模型数」初始全为 0，由产品决定是否在首个开通批次完成后自然生长（Q7）。
